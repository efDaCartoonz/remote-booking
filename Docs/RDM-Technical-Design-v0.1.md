# 1. Назначение документа

## 1.1. Цель

Документ описывает техническую реализацию MVP системы Remote Desktop Manager на основании согласованного SRS v1.0.

Цель документа — дать разработке достаточно конкретную основу для старта кода:

- определить состав сервисов;
- зафиксировать выбранный стек;
- описать границы backend, frontend, фрейма Omnidesk и фоновых задач;
- описать базовую модель данных;
- определить API-контуры;
- определить подход к интеграциям, безопасности, деплою, backup и мониторингу.

## 1.2. Границы документа

Документ не является финальной низкоуровневой спецификацией всех классов, SQL-миграций и экранов. Он задаёт техническую архитектуру MVP.

После согласования этого документа следующими рабочими артефактами должны стать:

- структура репозитория;
- `docker-compose.yml`;
- базовый FastAPI-проект;
- базовый Vue-проект;
- первая схема PostgreSQL через миграции;
- минимальный набор API endpoint-ов;
- технические README для запуска dev-окружения.

# 2. Архитектурный подход

## 2.1. Общая схема

MVP реализуется как модульный веб-монолит с отдельным frontend-приложением и отдельными worker-процессами для фоновых задач.

```text
┌────────────────────────────┐
│ Внутренние пользователи    │
│ L1 / L2 / руководитель     │
│ администратор              │
└──────────────┬─────────────┘
               │
               ▼
┌────────────────────────────┐
│ Vue 3 Internal UI          │
└──────────────┬─────────────┘
               │ HTTPS / API
               ▼
┌────────────────────────────┐
│ FastAPI Backend            │
│ бизнес-логика RDM          │
└───────┬────────────┬───────┘
        │            │
        ▼            ▼
┌──────────────┐  ┌──────────────┐
│ PostgreSQL   │  │ Redis        │
│ данные RDM   │  │ broker Celery│
│ outbox       │  │ cache/temp   │
└──────────────┘  └──────┬───────┘
                         ▼
                  ┌──────────────┐
                  │ Celery Worker│
                  │ Beat/Scheduler│
                  └──────┬───────┘
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ Omnidesk API │  │ Telegram Bot │  │ Bitrix24 Bot │
└──────────────┘  └──────────────┘  └──────────────┘
```

Клиентский личный кабинет Omnidesk встраивает отдельный frontend-фрейм RDM:

```text
┌──────────────────────────────────────────────┐
│ Omnidesk: страница текущего тикета клиента   │
│ URL содержит номер тикета                    │
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │ RDM Client Frame                       │  │
│  │ - показывает карточки текущего тикета  │  │
│  │ - позволяет создать новую карточку     │  │
│  │ - не даёт переносить/отменять          │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

## 2.2. Почему модульный монолит

Для MVP не требуется микросервисная архитектура. Основная сложность находится в бизнес-правилах карточек, назначений, статусов, интеграции с Omnidesk и уведомлений.

Модульный монолит даёт:

- меньше инфраструктурной сложности;
- единые транзакции PostgreSQL;
- проще тестировать жизненный цикл карточки;
- проще запускать dev/stage/prod через Docker Compose;
- проще сопровождать на первом этапе.

Разделение на сервисы возможно позже, если появится реальная нагрузка или организационная необходимость.

# 3. Компоненты системы

| Компонент | Технология | Ответственность |
|---|---|---|
| Backend API | FastAPI | Внутренний API, API фрейма, бизнес-правила, авторизация, интеграции |
| Internal UI | Vue 3 + Vite | Интерфейс L1, L2, руководителя, администратора |
| Client Frame UI | Vue 3 + Vite | Встраиваемый интерфейс в тикете Omnidesk |
| Database | PostgreSQL | Основные данные RDM, история, аудит, outbox |
| Worker | Celery | Напоминания, уведомления, синхронизация, повторы, продления |
| Broker | Redis | Техническая очередь Celery |
| Scheduler | Celery Beat | Периодические задачи |
| Reverse Proxy | Nginx или Caddy | HTTPS, маршрутизация frontend/backend |
| Monitoring | Prometheus + Grafana | Метрики и дашборды |
| Error Tracking | Sentry или совместимый инструмент | Ошибки backend/frontend |

## 3.1. Внутренний переход из уведомления

Внутренний frontend использует маршрут `/cards/{public_id}` и same-origin API. Nginx обслуживает SPA, а запросы `/api/` проксирует в backend; отдельный адрес backend в браузерный код не попадает. Вход выполняется через `/api/v1/auth/login`, текущая сессия проверяется `/api/v1/auth/me`, завершение — `/api/v1/auth/logout`. После входа сохраняется исходный маршрут карточки.

Публичный базовый адрес ссылки уведомления задаётся переменной `NOTIFICATION_CARD_BASE_URL` в `.env`. Для RPi stage это адрес доверенной LAN с портом frontend, для VPS — HTTPS-домен. `AUTH_COOKIE_SECURE=false` допустим только на доверенной LAN; в VPS используется `true`. UI показывает отдельные состояния `401`, `403` и `404`, загружает карточку только через существующий `GET /api/v1/cards/{card_id}` и не меняет backend lifecycle, scanner или delivery.

# 4. Backend

## 4.1. Стек backend

Рекомендуемый стек backend:

- Python 3.12 или актуальная стабильная версия Python на момент старта разработки;
- FastAPI;
- Pydantic для схем входа/выхода;
- SQLAlchemy 2.x для работы с PostgreSQL;
- Alembic для миграций;
- Celery для фоновых задач;
- pytest для тестов;
- ruff для форматирования и статической проверки.

## 4.2. Логические модули backend

```text
app/
├── api/
│   ├── internal/
│   ├── frame/
│   ├── integrations/
│   └── health/
├── core/
│   ├── config/
│   ├── security/
│   ├── errors/
│   └── logging/
├── domain/
│   ├── cards/
│   ├── assignments/
│   ├── schedules/
│   ├── notifications/
│   ├── omnidesk/
│   └── audit/
├── db/
│   ├── models/
│   ├── migrations/
│   └── repositories/
├── services/
│   ├── card_service.py
│   ├── assignment_service.py
│   ├── schedule_service.py
│   ├── omnidesk_service.py
│   └── notification_service.py
└── workers/
    ├── tasks/
    └── beat_schedule.py
```

## 4.3. Основные backend-принципы

- Все изменения состояния карточки выполняются только через backend.
- Все переходы статусов проверяются сервером.
- Frontend не принимает бизнес-решений, а только показывает доступные действия.
- Все важные изменения пишутся в историю карточки и аудит.
- Все внешние интеграционные действия сначала фиксируются в PostgreSQL, затем выполняются worker-ом.
- Redis не используется как источник истины для бизнес-данных.

# 5. Frontend

## 5.1. Стек frontend

Рекомендуемый стек frontend:

- Vue 3;
- Vite;
- TypeScript;
- Pinia для состояния frontend;
- Vue Router для внутреннего интерфейса;
- UI-компоненты на базе выбранной библиотеки после прототипа календаря;
- Playwright для e2e-проверок ключевых сценариев.

## 5.2. Два frontend-контура

Frontend должен иметь два логических контура:

1. Внутренний интерфейс RDM.
2. Клиентский фрейм для Omnidesk.

Они могут быть в одном frontend-проекте, но должны иметь разные маршруты и разные API-клиенты.

Пример:

```text
/app/*      внутренний интерфейс RDM
/frame/*    клиентский фрейм Omnidesk
```

## 5.3. Внутренний интерфейс

Внутренний интерфейс покрывает:

- список карточек;
- карточку подключения;
- календарь;
- действия L1;
- действия L2;
- действия руководителя;
- администрирование пользователей, графиков, справочников и интеграций;
- отчёты и диагностические экраны.

# 6. Клиентский фрейм Omnidesk

## 6.1. Назначение

Клиентский фрейм RDM встраивается в страницу текущего тикета Omnidesk.

Фрейм нужен для двух операций:

- показать клиенту карточки удалённого подключения по текущему тикету;
- позволить клиенту создать новую карточку по текущему тикету, если это разрешено.

Фрейм не должен позволять клиенту:

- переносить карточку;
- менять дату, время или длительность существующей карточки;
- отменять карточку;
- видеть внутренние причины отказов L2;
- видеть графики сотрудников;
- видеть внутренние идентификаторы RDM.

Перенос и отмена выполняются через сообщение клиента в текущем тикете Omnidesk и дальнейшую обработку сотрудниками.

## 6.2. Получение номера тикета

На текущем тестовом ЛК Omnidesk подтверждён URL страницы тикета вида:

```text
https://iridi.omnidesk.ru/l_rus/user/cases/record/829-447027/
```

Для MVP фрейм может получать номер тикета из:

- URL страницы Omnidesk;
- DOM страницы Omnidesk, если это потребуется для совместимости.

Номер тикета из URL или DOM не считается доказательством доступа. Это только входной контекст.

## 6.3. Серверные проверки фрейма

Перед выдачей данных по карточкам backend должен:

1. Получить номер тикета из запроса фрейма.
2. Запросить тикет в Omnidesk API.
3. Проверить, что тикет существует.
4. Проверить, что тикет не удалён и не находится в спаме.
5. Получить `user_id`, статус, тип, категорию и другие доступные поля тикета.
6. Вернуть только карточки RDM, связанные с этим тикетом.

Если тикет закрыт и клиент создаёт новую карточку, backend должен сначала перевести тикет в «Открытое» через Omnidesk API.

## 6.4. Frame-session

Для MVP рекомендуется использовать короткоживущую frame-session RDM.

Назначение frame-session:

- не авторизовать клиента как отдельного пользователя RDM;
- связать несколько запросов фрейма с одним текущим тикетом;
- снизить количество повторных проверок Omnidesk API;
- ограничить срок действия контекста фрейма.

Frame-session должна быть привязана к:

- номеру тикета;
- времени создания;
- Origin/Referer, если браузер их передал;
- сроку действия;
- минимальному набору разрешений: чтение карточек текущего тикета и создание новой карточки.

Важно: frame-session не должна давать доступ к другим тикетам.

## 7.4. Целостность данных

Обязательные ограничения:

- у одного L2 не может быть двух активных пересекающихся резервирований;
- изменение статуса карточки и запись события истории выполняются в одной транзакции;
- назначение L2 и резервирование времени выполняются в одной транзакции;
- outbox-событие создаётся в той же транзакции, что и бизнес-изменение;
- карточка не удаляется физически в штатном процессе.

# 8. API-контракт

## 8.1. Группы API

| Контур | Назначение |
|---|---|
| Internal API | Интерфейсы сотрудников |
| Frame API | Клиентский фрейм Omnidesk |
| Integration API | Входящие события Omnidesk и служебные интеграции |
| Health API | Проверки живости, готовности и метрики |

## 8.2. Internal API

Примерный набор endpoint-ов:

```text
POST   /api/v1/auth/login
POST   /api/v1/auth/logout
GET    /api/v1/auth/me
```

## 8.3. Frame API

Frame API должен быть минимальным.

Разрешено:

```text
POST   /frame/v1/session
GET    /frame/v1/tickets/{case_number}/cards
POST   /frame/v1/tickets/{case_number}/cards
GET    /frame/v1/tickets/{case_number}/cards/{card_id}
```

Запрещено:

```text
PATCH  /frame/v1/tickets/{case_number}/cards/{card_id}/time
POST   /frame/v1/tickets/{case_number}/cards/{card_id}/cancel
DELETE /frame/v1/tickets/{case_number}/cards/{card_id}
```

Создание карточки через Frame API должно принимать:

- номер текущего тикета;
- дату и время начала;
- длительность;
- описание;
- контактные данные, актуализированные клиентом;
- часовой пояс клиента;
- источник часового пояса.

## 8.4. Health API

```text
GET /health/live
GET /health/ready
GET /metrics
```

`/health/live` проверяет, что процесс отвечает.

`/health/ready` проверяет готовность зависимостей: PostgreSQL, Redis, возможность выполнить базовую внутреннюю операцию.

`/metrics` отдаёт метрики для Prometheus.

# 9. Фоновые задачи и очереди

## 9.1. Очереди Celery

Рекомендуемые очереди:

| Очередь | Назначение |
|---|---|
| `default` | Общие фоновые задачи |
| `notifications` | Telegram, Битрикс24, клиентские уведомления через Omnidesk |
| `omnidesk` | Синхронизация с Omnidesk |
| `scheduler` | Проверка сроков, напоминания, автопродления |
| `maintenance` | Очистка временных данных, технические задачи |

## 9.2. Периодические задачи

Celery Beat должен запускать:

- проверку карточек в статусе «Создано» для автоназначения;
- напоминания L2 каждые 10 минут по назначенным карточкам;
- напоминания L1 по отклонённым карточкам;
- проверку окончания планового интервала;
- автопродление карточек в статусе «Выполняется»;
- повторную доставку outbox-событий;
- техническую очистку истёкших frame-session.

## 9.3. Outbox

Outbox нужен для надёжности.

Пример:

1. Карточка перешла в «Подтверждено».
2. В той же транзакции создано событие `card.confirmed`.
3. Worker читает `outbox_events`.
4. Worker отправляет уведомления и синхронизирует Omnidesk.
5. После успеха событие помечается обработанным.
6. При ошибке событие остаётся для повторной обработки.

# 10. Интеграция с Omnidesk

## 10.1. Используемые возможности Omnidesk

RDM должен использовать Omnidesk как внешнюю систему тикетов.

Основные операции:

- получить тикет по номеру или ID;
- проверить статус тикета;
- проверить признаки `deleted` и `spam`;
- получить `user_id` клиента;
- получить тип и категорию обращения, если доступны;
- перевести закрытый тикет в статус «Открытое»;
- изменить ответственного сотрудника;
- добавить внутреннюю заметку;
- прочитать сообщения и историю действий при необходимости;
- учитывать лимиты API.

## 10.2. Правила синхронизации

- RDM не меняет группу Omnidesk.
- RDM может менять ответственного Omnidesk на L2 или L1 согласно процессу.
- RDM не закрывает тикет после завершения подключения.
- Результат подключения фиксируется внутренней заметкой.
- Клиентское уведомление за 15 минут отправляется через тикет Omnidesk по шаблону.
- При недоступности Omnidesk карточка RDM не теряется, а синхронизация повторяется фоном.

## 10.3. Лимиты API

Интеграционный клиент Omnidesk должен читать заголовки:

- `rate_limit_per_minute`;
- `api_calls_left`;
- `retry_after`.

При приближении к лимиту worker должен замедлять повторные запросы.

При ответе `429 Too Many Requests` задача должна быть отложена на время из `retry_after`.

# 11. Уведомления

## 11.1. Каналы

MVP использует:

- Telegram-бот;
- бот Битрикс24;
- сообщения/заметки Omnidesk для клиентского контекста.

## 11.2. Принципы

- Уведомление не должно изменять бизнес-статус само по себе.
- Каждая попытка доставки фиксируется.
- Ошибка доставки не должна ломать карточку.
- Повторная доставка выполняется фоновыми задачами.
- Шаблоны уведомлений должны настраиваться администратором.

# 12. Авторизация и безопасность

## 12.1. Внутренние пользователи

Внутренние пользователи авторизуются локально в RDM.

Рекомендуемый подход:

- логин + пароль;
- хранение хэшей паролей через Argon2id или bcrypt;
- HTTP-only secure cookie для session token;
- ограниченный срок жизни сессии;
- серверная проверка роли на каждое изменяющее действие;
- журналирование входа, выхода и критичных действий.

## 12.2. Клиентский фрейм

Клиент не получает отдельную учётную запись RDM.

Для MVP принимается ограниченная схема:

- клиент уже авторизован в Omnidesk для просмотра текущего тикета;
- RDM получает номер текущего тикета из контекста страницы;
- RDM проверяет тикет через Omnidesk API;
- RDM отдаёт только карточки текущего тикета;
- Frame API не содержит операций переноса и отмены;
- Frame API не раскрывает внутренние данные RDM.

Остаточный риск: номер тикета не является полноценной криптографической авторизацией. Риск снижается ограничением данных, проверками Omnidesk, CORS/Origin, rate limit, frame-session и отсутствием изменяющих операций кроме создания новой карточки.

# 13. Время и часовые пояса

## 13.1. Хранение

Все ключевые моменты времени хранятся в PostgreSQL в нормализованном виде через `timestamptz`.

Система хранит:

- плановое начало;
- плановое окончание;
- длительность;
- фактическое начало;
- фактическое окончание;
- часовой пояс клиента на момент создания;
- часовой пояс внутреннего пользователя для отображения.

## 13.2. Клиентский часовой пояс

Фрейм должен определять часовой пояс браузера:

```javascript
Intl.DateTimeFormat().resolvedOptions().timeZone
```

После определения frontend показывает клиенту часовой пояс в форме.

Клиент может изменить часовой пояс вручную.

Если часовой пояс не определён и не выбран вручную, используется `Europe/Moscow`.

## 13.3. Отображение

Пример:

- клиент в Москве создаёт подключение на `13:00 Europe/Moscow`;
- инженер в Екатеринбурге видит `15:00 Asia/Yekaterinburg`;
- в карточке сохраняется, что клиент создавал подключение в `Europe/Moscow`.

# 15. Backup и восстановление

## 15.1. MVP backup

Для MVP требуется:

- регулярный backup PostgreSQL;
- хранение backup вне контейнера PostgreSQL;
- журнал успешности backup;
- периодическая проверка восстановления на stage.

## 15.2. Развитие

Если RDM становится критичной производственной системой, backup должен быть расширен до WAL/PITR, чтобы можно было восстановиться на конкретный момент времени.

# 16. Мониторинг и диагностика

## 16.1. Метрики

Prometheus должен собирать:

- доступность backend;
- время ответа API;
- количество ошибок;
- размер очередей Celery;
- количество необработанных outbox-событий;
- ошибки Omnidesk API;
- ошибки Telegram/Битрикс24;
- количество карточек по статусам;
- количество просроченных карточек.

## 16.2. Дашборды

Grafana должна показывать:

- общее состояние системы;
- состояние очередей;
- состояние интеграций;
- состояние базы данных;
- динамику ошибок;
- бизнес-показатели RDM.

## 16.3. Ошибки приложения

Sentry или совместимый инструмент должен фиксировать:

- исключения backend;
- ошибки frontend;
- контекст запроса без секретов;
- версию приложения;
- окружение.

# 20. Приложения

## Приложение А. Минимальный состав MVP

Минимальный технический MVP считается готовым, если:

- backend запускается в Docker Compose;
- frontend запускается в Docker Compose;
- PostgreSQL и Redis работают в составе окружения;
- внутренний пользователь может войти в RDM;
- клиентский фрейм может показать карточки текущего тикета;
- клиентский фрейм может создать новую карточку;
- карточка проходит автоматическое назначение L2;
- L2 может подтвердить, отклонить, начать и завершить карточку;
- L1 получает отклонённую карточку;
- Omnidesk получает внутренние заметки;
- уведомления отправляются через выбранные каналы;
- основные действия пишутся в аудит;
- есть backup PostgreSQL;
- есть health-check и базовые метрики.

## Приложение Б. Принятые ограничения MVP

- Клиент не авторизуется отдельно в RDM.
- Клиент не переносит и не отменяет карточки через фрейм RDM.
- Клиентский API фрейма не раскрывает внутренние данные.
- Redis не используется как постоянное хранилище бизнес-данных.
- Группы Omnidesk не используются как источник ролей RDM.
- Kubernetes не используется на MVP.
- SSO/OIDC не используется на MVP.
