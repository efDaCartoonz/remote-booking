# 1. Введение

## 1.1. Назначение документа

Настоящий документ описывает требования к системе Remote Desktop Manager, далее RDM. Документ предназначен для перехода от согласованной концепции к проектированию, разработке, тестированию и приемке системы.

SRS фиксирует:

- границы системы;
- роли пользователей;
- состояния карточки удалённого подключения;
- функциональные требования;
- требования к интерфейсам и API;
- требования к данным и журналированию;
- требования к интеграции с Omnidesk;
- требования к уведомлениям;
- нефункциональные требования;
- критерии приемки.

Документ не является детальным техническим проектом. Он фиксирует архитектурные решения MVP на уровне SRS, но не определяет физическую схему базы данных, полную схему CI/CD, точные параметры инфраструктуры и детальную реализацию каждого интеграционного сценария. Эти решения должны быть уточнены на этапе технического проекта.

## 1.2. Основание

Документ подготовлен на основании концепции:

**Docs/RDM-Concept.md. Концепция сервиса Remote Desktop Manager.**

Все согласованные бизнес-решения версии 1.0 считаются исходными требованиями для настоящего SRS, если в этом документе явно не указано иное.

## 1.3. Цель системы

RDM должен обеспечить управляемое бронирование, назначение, выполнение и завершение удалённых подключений инженерами технической поддержки с учётом расписания, доступности сотрудников, прав ролей, интеграции с Omnidesk и обязательного уведомления участников процесса.

## 1.4. Целевая аудитория документа

Документ предназначен для:

- владельца продукта;
- руководителей технической поддержки;
- специалистов L1;
- инженеров L2;
- аналитиков;
- backend-разработчиков;
- frontend-разработчиков;
- тестировщиков;
- администраторов системы;
- специалистов, отвечающих за интеграцию с Omnidesk, Telegram и Битрикс24.

# 2. Общее описание системы

## 2.1. Назначение RDM

RDM является специализированным сервисом для управления удалёнными подключениями. Система не заменяет Omnidesk как тикетную систему и не становится самостоятельной системой ведения обращений.

RDM отвечает за:

- создание карточек удалённых подключений;
- планирование даты, времени и длительности подключения;
- автоматическое и ручное назначение инженера L2;
- обработку отказов инженеров;
- обработку отсутствия ответа инженера;
- сопровождение отклонённых и просроченных карточек специалистами L1;
- предотвращение пересекающихся назначений одного инженера;
- фиксацию выполнения работ;
- уведомления;
- синхронизацию согласованных событий с Omnidesk;
- хранение истории и журнала действий.

## 2.2. Границы MVP

В MVP входит:

- веб-интерфейс для внутренних пользователей;
- клиентский фрейм для личного кабинета Omnidesk;
- создание карточки клиентом, L1, L2 и руководителем;
- автоматическое распределение инженеров L2;
- автоматическое распределение сопровождения L1;
- ручное назначение и переназначение руководителем;
- жизненный цикл карточки от создания до завершения или отмены;
- обработка срочных подключений;
- обработка ретроспективных подключений L2;
- интеграция с Omnidesk по согласованным событиям;
- уведомления через Telegram-бота и бота Битрикс24;
- административное управление пользователями, ролями, графиками, участием в распределении и производственным календарём;
- аудит действий.

## 2.3. Не входит в MVP

В MVP не входит:

- замена Omnidesk;
- полноценная переписка с клиентом внутри RDM;
- интеграция с Outlook Calendar и Google Calendar;
- автоматическая оптимизация загрузки инженеров по сложности задач;
- автоматическое принятие решения за руководителя при кадровых или организационных исключениях;
- мобильное приложение;
- биллинг;
- учёт фактической занятости инженера по всем внешним системам компании;
- автоматическое подключение к объектам клиента.

## 2.4. Классы пользователей

| Класс пользователя | Описание |
|---|---|
| Клиент | Пользователь личного кабинета Omnidesk, создающий, переносящий или отменяющий подключение по своим тикетам. |
| Специалист L1 | Сотрудник первой линии, создающий карточки, согласующий время с клиентом, сопровождающий отклонённые и просроченные карточки. |
| Инженер L2 | Инженер, выполняющий удалённое подключение, подтверждающий или отклоняющий назначение, создающий карточки для себя. |
| Руководитель | Пользователь, управляющий назначениями, распределением, исключениями, составом участников и критичными ситуациями. |
| Администратор | Пользователь, выполняющий техническую настройку системы на основании согласованных решений. |
| Система | Автоматические процессы RDM: распределение, проверки, напоминания, синхронизация, журналирование. |

## 2.5. Операционная среда

RDM должен быть реализован как веб-система с серверной частью и API на Python, основной базой данных PostgreSQL и отдельным frontend-приложением.

Для MVP фиксируются следующие базовые архитектурные решения:

- backend: FastAPI;
- frontend: Vue 3 + Vite;
- авторизация внутренних пользователей: локальные пользователи RDM;
- фоновые задачи: Celery;
- техническая очередь фоновых задач: Redis;
- надёжная фиксация бизнес-событий: PostgreSQL outbox;
- окружения: dev, stage, prod через Docker Compose;
- резервное копирование: PostgreSQL backup;
- мониторинг: Prometheus + Grafana + Sentry;
- поддерживаемые браузеры: Chrome, Edge, Safari; Firefox в режиме best effort.

## 2.6. Основные ограничения

| Ограничение | Значение |
|---|---|
| Минимальное время до обычного подключения | 120 минут |
| Длительность по умолчанию | 60 минут |
| Минимальная длительность | 30 минут |
| Максимальная длительность | 12 часов |
| Максимальный горизонт планирования | 14 календарных дней |
| Шаг календарной сетки | 15 минут |
| Требование к точному времени | Время начала и длительность могут быть не кратны 15 минутам |
| Базовый часовой пояс | Europe/Moscow |
| Дополнительный пользовательский часовой пояс | Настраивается для каждого участника |
| Нерабочие дни | Выходные и праздничные дни по производственному календарю РФ с возможностью корректировки |

## 2.7. Справочный статус реализации MVP на 3 сентября 2026 г.

Этот раздел не является набором требований и не означает приёмку всех связанных требований SRS. Он показывает, какие части уже существуют в коде и какие из них подтверждены stage-проверкой на Raspberry Pi.

| Область | Реализовано | Подтверждено на stage | Не входит в подтверждение |
|---|---|---|---|
| PostgreSQL и первая Alembic-миграция | Да | Да | Последующие миграции отсутствуют |
| Локальная авторизация внутренних пользователей | Да | Доступность backend подтверждена | Полный набор сценариев UI |
| Карточка и статусы backend | Базовый API и история | Частично, через Frame/L2 smoke | Полный набор ролей и исключений |
| Frame API и Omnidesk | Core-сценарий с `case_id`, Redis-сессией, серверной сверкой и reopen | Да, на безопасном тикете | Rate limit, frontend и SSO/JWT |
| Первичное Round Robin распределение L2 | Да | Да, в изолированном rollback smoke | Отказы L2, повторные циклы, L1 |
| Уведомления, L1-сопровождение, frontend, исходящая синхронизация Omnidesk | Нет | Нет | Требования остаются обязательными для MVP |

# 3. Термины и сокращения

| Термин | Определение |
|---|---|
| RDM | Remote Desktop Manager, система управления удалёнными подключениями. |
| Карточка удалённого подключения | Основной объект RDM, содержащий сведения о планировании, участниках, ответственном инженере, связи с Omnidesk, состоянии, выполнении и истории конкретного подключения. |
| Тикет Omnidesk | Обращение клиента в Omnidesk, с которым связана карточка RDM. |
| Клиентский фрейм | Встроенный в личный кабинет Omnidesk интерфейс RDM для клиента. |
| L1 | Специалист первой линии поддержки. |
| L2 | Инженер второй линии поддержки. |
| Руководитель | Пользователь, имеющий право управлять назначениями и исключениями в рамках своей компетенции. |
| Сопровождающий L1 | Специалист L1, отвечающий за связь с клиентом по отклонённой или просроченной карточке. |
| Ответственный инженер | Инженер L2, назначенный на карточку в текущий момент. |
| Автоматическое распределение | Процесс выбора сотрудника из допустимых участников глобальной очереди. |
| Глобальная очередь | Единая очередь распределения для роли L1 или L2. |
| Round Robin | Алгоритм поочерёдного выбора следующего участника очереди с учётом доступности и правил допуска. |
| Участник распределения | Сотрудник, включённый руководителем в автоматическое распределение. |
| Доступный сотрудник | Сотрудник, который участвует в распределении и доступен на указанный временной интервал по графику, отсутствиям и текущим назначениям. |
| Отказ инженера | Зафиксированное решение назначенного инженера не выполнять подключение в предложенное время. |
| Неуспешный цикл назначения | Цикл, в котором допустимых инженеров не было изначально либо все сформированные кандидаты отказались. |
| Просрочка | Служебный признак карточки в статусе «Назначено», у которой плановый интервал закончился без решения L2. |
| Срочное подключение | Внеплановое подключение к приоритетному клиенту или по аварии на действующем объекте. |
| Ретроспективное подключение | Подключение, созданное инженером L2 после фактического начала или окончания работ. |
| Продление сессии | Автоматическое увеличение планового интервала карточки в статусе «Выполняется», если работы начались, но не могут быть завершены в исходно запланированный срок. |
| Производственный календарь | Календарь рабочих, выходных и праздничных дней РФ с возможностью корректировки администратором. |

# 4. Роли и модель доступа

DATA-002 MUST. Карточка должна хранить связь с тикетом Omnidesk, если карточка создана по существующему тикету или если тикет был создан в рамках интеграционного сценария.

DATA-003 MUST. Карточка должна хранить плановое время начала и окончания в нормализованном виде, длительность, часовой пояс клиента на момент создания при его наличии и должна отображать время в часовом поясе текущего пользователя.

DATA-011 MUST. Карточка должна хранить счётчик неуспешных циклов назначения.

DATA-012 MUST. Карточка должна хранить критичность.

DATA-013 MUST. Карточка должна хранить описание задачи.

DATA-014 MUST. Карточка должна хранить перечень выполненных работ и результат перед завершением.

DATA-015 MUST. Карточка должна хранить историю изменений ключевых полей.

DATA-016 MUST. Карточка должна хранить выбранный результат подключения как значение из администрируемого справочника.

DATA-017 MUST. Карточка должна хранить текстовый комментарий инженера к результату подключения.

DATA-018 MUST. Карточка должна хранить фактическую продолжительность подключения после завершения или корректировки.

DATA-019 MUST. Карточка должна хранить количество автоматических продлений выполняющейся сессии.

DATA-020 MUST. Карточка должна хранить признак и детали коллизии, если она возникла из-за продления выполняющейся сессии.

# 6. Жизненный цикл карточки

## 6.1. Статусы

| Статус | Назначение |
|---|---|
| Создано | Техническое состояние карточки во время автоматического распределения. |
| Назначено | Ответственный L2 определён, карточка ожидает решения инженера или начала работ. |
| Подтверждено | Ответственный L2 подтвердил выполнение подключения в назначенное время. |
| Отклонено | На предложенное время нет допустимых инженеров либо все допустимые инженеры отказались. |
| Выполняется | Подключение находится в процессе выполнения. |
| Завершено | Подключение выполнено и результат зафиксирован. |
| Отменено | Подключение отменено допустимым участником процесса. |

## 6.2. Общие правила статусов

REQ-FR-009 MUST. Статус «Создано» должен использоваться только как технический статус автоматического распределения.

REQ-FR-010 MUST. Пользователи не должны иметь возможность изменить дату, время или отменить карточку в статусе «Создано».

REQ-FR-011 MUST. Система должна автоматически переводить карточку из «Создано» в «Назначено», если найден допустимый инженер L2.

REQ-FR-012 MUST. Система должна автоматически переводить карточку из «Создано» в «Отклонено», если допустимых инженеров L2 нет.

REQ-FR-013 MUST. Отказ одного инженера L2 не должен переводить карточку в статус «Отклонено».

REQ-FR-014 MUST. Статус «Отклонено» должен устанавливаться только если нет допустимых инженеров L2 для выбранного времени либо все допустимые инженеры отказались.

REQ-FR-015 MUST. Конечные статусы «Завершено» и «Отменено» должны быть неизменяемыми для обычных пользовательских действий.

| Из статуса | В статус | Инициатор | Условие |
|---|---|---|---|
| Создано | Назначено | Система | Найден допустимый L2. |
| Создано | Отклонено | Система | Допустимых L2 нет. |
| Назначено | Назначено | Система | Текущий L2 отказался, найден следующий L2. |

| Подтверждено | Выполняется | L2, руководитель | Подключение начато. |

## 6.4. Начальные статусы

REQ-FR-016 MUST. Карточка, созданная клиентом, должна начинаться со статуса «Создано».

REQ-FR-017 MUST. Карточка, созданная L1, должна начинаться со статуса «Создано».

REQ-FR-018 MUST. Карточка, созданная руководителем с выбранным значением «Автоматически», должна начинаться со статуса «Создано».

REQ-FR-019 MUST. Карточка, созданная руководителем с выбранным конкретным L2, должна сразу получать статус «Назначено».

REQ-FR-020 MUST. Карточка, созданная L2 для себя как обычная или срочная, должна сразу получать статус «Назначено».

REQ-FR-021 MUST. Ретроспективная карточка L2, у которой конец подключения раньше текущего времени, должна сразу получать статус «Завершено» при наличии перечня выполненных работ и результата.

REQ-FR-022 MUST. Ретроспективная карточка L2, у которой подключение ещё находится в плановом интервале, должна сразу получать статус «Выполняется».

# 7. Функциональные требования

## 7.1. Создание карточки

REQ-FR-023 MUST. Система должна позволять клиенту создать карточку удалённого подключения из клиентского фрейма Omnidesk по текущему обращению, включая закрытое обращение после перевода статуса обращения из «Закрытое» в «Открытое» через Omnidesk API.

REQ-FR-024 MUST. Система должна позволять L1 создать карточку по обращению клиента.

REQ-FR-025 MUST. Система должна позволять руководителю создать карточку с ручным выбором L2 или с выбором значения «Автоматически».

REQ-FR-026 MUST. Система должна позволять L2 создать карточку только для себя.

REQ-FR-027 MUST. Система должна позволять L2 создать ретроспективную карточку только для себя.

REQ-FR-028 MUST. При создании обычной карточки система должна проверять минимальное время до подключения 120 минут.

REQ-FR-029 MUST. При создании срочной карточки система должна применять отдельный сценарий срочности и фиксировать основание срочности.

REQ-FR-030 MUST. Система должна проверять максимальный горизонт планирования 14 календарных дней.

REQ-FR-031 MUST. Система должна проверять минимальную длительность 30 минут.

REQ-FR-032 MUST. Система должна проверять максимальную длительность 12 часов.

REQ-FR-033 MUST. Если длительность не указана, система должна использовать длительность по умолчанию 60 минут.

REQ-FR-034 MUST. Система должна учитывать производственный календарь РФ и рабочий график при проверке допустимости времени.

REQ-FR-035 MUST. Система должна позволять создать карточку на выходной, праздничный день или вне рабочего времени только по правилам вне рабочего времени или срочности.

## 7.2. Автоматическое назначение L2

REQ-FR-036 MUST. Система должна автоматически назначать инженера L2 для карточек, пришедших в статус «Создано».

REQ-FR-037 MUST. Автоматическое назначение L2 должно использовать глобальную очередь Round Robin.

REQ-FR-038 MUST. В автоматическое назначение L2 должны попадать только сотрудники, включённые в распределение руководителем.

REQ-FR-039 MUST. В автоматическое назначение L2 должны попадать только сотрудники, доступные на весь плановый интервал карточки.

REQ-FR-040 MUST. Система должна исключать из кандидатов L2, у которых есть пересекающееся удалённое подключение на выбранный интервал.

REQ-FR-041 MUST. Система должна исключать из текущего цикла L2, которые уже отказались от этой карточки на это же время.

REQ-FR-042 MUST. После выбора L2 система должна назначить его ответственным и перевести карточку в «Назначено».

REQ-FR-043 MUST. Назначение карточки в статус «Назначено» должно резервировать плановый интервал инженера.

REQ-FR-044 MUST. Система не должна назначать одному инженеру несколько удалённых подключений на одно и то же время.

REQ-FR-045 MUST. Алгоритм не должен использовать условную минимальную загрузку как обязательный критерий MVP.

## 7.3. Решение L2

REQ-FR-046 MUST. Назначенный L2 должен иметь возможность подтвердить назначенную карточку.

REQ-FR-047 MUST. Назначенный L2 должен иметь возможность отклонить назначенную карточку с обязательным указанием причины.

REQ-FR-048 MUST. После подтверждения L2 система должна перевести карточку в «Подтверждено».

REQ-FR-049 MUST. После отказа L2 система должна сохранить отказ и причину.

REQ-FR-050 MUST. После отказа L2 система должна автоматически выбрать следующего допустимого L2 из текущего цикла.

REQ-FR-051 MUST. Если следующий L2 найден, карточка должна остаться в статусе «Назначено» с новым ответственным.

REQ-FR-052 MUST. Если все допустимые L2 отказались, карточка должна перейти в «Отклонено».

REQ-FR-053 MUST. Если руководитель отклоняет карточку за инженера, система должна требовать причину и фиксировать действие как действие руководителя.

REQ-FR-054 MUST. Отклонение руководителем за инженера не должно автоматически исключать инженера из глобального распределения.

## 7.4. Обработка отсутствия ответа L2

REQ-FR-055 MUST. Отсутствие ответа L2 не должно считаться отказом.

REQ-FR-056 MUST. Система должна напоминать назначенному L2 о необходимости решения каждые 10 минут до начала подключения и в течение всего планового интервала.

REQ-FR-057 MUST. При втором напоминании L2 система должна уведомить руководителя.

REQ-FR-058 MUST. После окончания планового интервала карточки в статусе «Назначено» система должна остановить напоминания L2.

REQ-FR-059 MUST. После окончания планового интервала без решения L2 система должна оставить статус «Назначено» и установить признак просрочки.

REQ-FR-060 MUST. После установки признака просрочки система должна назначить сопровождающего L1 по правилам глобального распределения L1.

REQ-FR-061 MUST. После установки признака просрочки система должна уведомить L1 и руководителя.

REQ-FR-062 MUST. Если доступных L1 нет, система должна уведомить руководителя о необходимости вывести в распределение других сотрудников.

## 7.5. Статус «Отклонено» и сопровождение L1

REQ-FR-063 MUST. Система должна переводить карточку в «Отклонено», если при первичном распределении нет ни одного допустимого L2.

REQ-FR-064 MUST. Система должна переводить карточку в «Отклонено», если все допустимые L2 отказались от предложенного времени.

REQ-FR-065 MUST. После перехода в «Отклонено» система должна назначить сопровождающего L1 по правилам глобального распределения L1.

REQ-FR-066 MUST. Если карточку создавал L1 и этот L1 доступен в момент назначения сопровождения, система должна вернуть карточку ему.

REQ-FR-067 MUST. Если создатель L1 недоступен или карточка создана другим способом, система должна выбрать сопровождающего L1 из глобальной очереди Round Robin L1.

REQ-FR-068 MUST. Если доступных L1 нет, карточка должна остаться в «Отклонено» без сопровождающего L1, а руководитель должен получить уведомление.

REQ-FR-069 MUST. Система должна уведомить L1 о необходимости связаться с клиентом и согласовать новое время.

REQ-FR-070 MUST. Система должна уведомить руководителя уже на первой итерации полного отказа или отсутствия кандидатов L2.

REQ-FR-071 MUST. L1 должен иметь возможность отметить, что клиент проинформирован о необходимости переноса подключения.

REQ-FR-072 MUST. L1 должен иметь возможность изменить дату, время и описание карточки после согласования с клиентом.

REQ-FR-073 MUST. После сохранения нового времени система должна сбросить список рассмотренных L2 для нового цикла назначения.

REQ-FR-074 MUST. После сохранения нового времени система должна запустить новый цикл назначения L2.

REQ-FR-075 MUST. При повторном неуспешном цикле система должна повысить критичность карточки и повторно уведомить руководителя.

## 7.6. Напоминания L1 по отклонённой карточке

REQ-FR-076 MUST. Пока карточка находится в «Отклонено» и требует обработки L1, система должна уведомлять сопровождающего L1 каждые 10 минут.

REQ-FR-077 MUST. После второго напоминания L1 без отметки «Клиент проинформирован» система должна уведомить руководителя.

REQ-FR-078 MUST. После уведомления руководителя система должна повторять эскалационное уведомление руководителю каждые 30 минут до отметки «Клиент проинформирован».

REQ-FR-079 MUST. После отметки «Клиент проинформирован» эскалационные уведомления руководителю должны прекратиться.

REQ-FR-080 MUST. После отметки «Клиент проинформирован» L1 должен иметь возможность увеличить интервал собственных напоминаний до 30 минут.

REQ-FR-081 MUST. Напоминания L1 должны продолжаться до назначения нового времени или отмены карточки.

REQ-FR-082 MUST. Если клиент самостоятельно изменил время карточки в «Отклонено», задача L1 по согласованию нового времени должна быть закрыта.

Точные якоря таймеров, поведение catch-up, snapshot конфигурации и параметры
scanner определены в `decisions/05-timer-reminders-and-escalations.md`.

## 7.7. Изменение времени

REQ-FR-083 MUST. Система должна разрешать изменение даты и времени только в статусах «Назначено», «Подтверждено» и «Отклонено».

REQ-FR-084 MUST. Система должна запрещать изменение даты и времени в статусе «Создано».

REQ-FR-085 MUST. Система должна запрещать изменение даты и времени в статусах «Выполняется», «Завершено» и «Отменено».

REQ-FR-086 MUST. Изменение времени должно проходить проверку правил планирования.

REQ-FR-087 MUST. При изменении времени карточки с назначенным L2 система должна снять прежнее резервирование времени.

REQ-FR-088 MUST. После изменения времени система должна запустить новый цикл назначения, если ответственный должен быть выбран автоматически.

REQ-FR-089 MUST. Если руководитель при изменении времени выбирает конкретного L2, карточка должна перейти в «Назначено» с выбранным L2 без автоматического распределения.

REQ-FR-090 MUST. Система должна фиксировать автора, прежнее время, новое время и причину изменения времени, если причина обязательна по сценарию.

## 7.8. Отмена карточки

REQ-FR-091 MUST. Система не должна позволять клиенту отменять карточку через клиентский фрейм RDM.

REQ-FR-092 MUST. Если клиенту требуется отменить или перенести подключение, клиент должен написать сообщение в текущем тикете Omnidesk, после чего изменение обрабатывается сотрудниками в рамках обычного процесса поддержки.

REQ-FR-093 MUST. Система должна разрешать отмену L1 по запросу клиента, если статус позволяет отмену.

REQ-FR-094 MUST. Система должна разрешать отмену L2 по запросу клиента, если статус позволяет отмену и карточка назначена этому L2.

REQ-FR-095 MUST. Система должна разрешать руководителю отменить незавершённую карточку, кроме статуса «Создано».

REQ-FR-096 MUST. При отмене система должна освободить резервирование времени L2.

REQ-FR-097 MUST. При отмене система должна остановить активные напоминания по карточке.

REQ-FR-098 MUST. При отмене система должна отправить необходимые уведомления и синхронизировать событие с Omnidesk.

## 7.9. Срочное подключение

REQ-FR-099 MUST. Система должна поддерживать создание срочного подключения.

REQ-FR-100 MUST. Срочное подключение должно требовать указания основания срочности.

REQ-FR-101 MUST. Срочное подключение должно применяться для внепланового подключения к приоритетному клиенту или по аварии на действующем объекте.

REQ-FR-102 MUST. При конфликте срочного подключения с запланированным подключением система должна зафиксировать информацию о коллизии.

REQ-FR-103 MUST. При конфликте срочного подключения система должна уведомить руководителя.

REQ-FR-104 MUST. При конфликте срочного подключения система должна уведомить L1 для информирования клиента о форс-мажоре.

REQ-FR-105 MUST. При конфликте срочного подключения система должна уведомить L2, чьё назначение затронуто конфликтом.

REQ-FR-106 MUST. При конфликте срочного подключения система должна автоматически запустить переназначение конфликтующей плановой карточки.

REQ-FR-107 MUST. Если для конфликтующей плановой карточки найден другой L2, карточка должна остаться или перейти в «Назначено» с новым ответственным.

REQ-FR-108 MUST. Если все L2 отказались от конфликтующей плановой карточки, карточка должна перейти в «Отклонено» и обрабатываться L1.

REQ-FR-109 MUST. Уведомление руководителя при срочном конфликте должно быть контрольным и не должно блокировать автоматическое переназначение.

## 7.10. Выполнение и завершение

REQ-FR-110 MUST. Назначенный или подтверждённый L2 должен иметь возможность начать выполнение подключения.

REQ-FR-111 MUST. Система должна переводить карточку в «Выполняется» при начале работ.

REQ-FR-112 MUST. Система должна фиксировать фактическое время начала работ.

REQ-FR-113 MUST. L2 должен иметь возможность завершить подключение.

REQ-FR-114 MUST. Система должна требовать перечень выполненных работ перед завершением.

REQ-FR-115 MUST. Система должна требовать выбор результата подключения из администрируемого справочника перед завершением.

REQ-FR-116 MUST. Система должна переводить карточку в «Завершено» только после заполнения обязательных данных о выполнении.

REQ-FR-117 MUST. Система должна фиксировать фактическое время завершения.

REQ-FR-118 MUST. Система должна фиксировать результат подключения в Omnidesk внутренней заметкой, не закрывая обращение и не отправляя публичный ответ клиенту автоматически.

## 7.11. Ретроспективное подключение

REQ-FR-119 MUST. Система должна позволять L2 регистрировать подключение задним числом только для себя.

REQ-FR-120 MUST. Ретроспективная карточка не должна проходить через статус «Создано».

REQ-FR-121 MUST. Ретроспективная карточка не должна запускать автоматическое распределение L2.

REQ-FR-122 MUST. Если конец ретроспективного подключения раньше текущего времени, система должна требовать перечень выполненных работ и результат при создании.

REQ-FR-123 MUST. Если конец ретроспективного подключения раньше текущего времени, система должна создать карточку сразу в статусе «Завершено».

REQ-FR-124 MUST. Если ретроспективное подключение ещё идёт, система должна создать карточку сразу в статусе «Выполняется».

REQ-FR-125 MUST. Система должна фиксировать ретроспективную регистрацию в журнале действий.

## 7.12. Календарь и доступность

REQ-FR-126 MUST. Система должна отображать календарь с сеткой 15 минут.

REQ-FR-127 MUST. Система должна позволять хранить и обрабатывать время начала, не кратное 15 минутам.

REQ-FR-128 MUST. Система должна позволять хранить и обрабатывать длительность, не кратную 15 минутам.

REQ-FR-129 MUST. Система должна проверять пересечение интервалов по фактическим временным значениям, а не только по визуальной сетке.

REQ-FR-130 MUST. Система должна учитывать рабочие графики сотрудников.

REQ-FR-131 MUST. Система должна учитывать отсутствия сотрудников.

REQ-FR-132 MUST. Система должна учитывать выходные и праздничные дни производственного календаря РФ.

REQ-FR-133 MUST. Система должна позволять администратору корректировать производственный календарь.

REQ-FR-134 MUST. Система должна хранить изменения производственного календаря в аудите.

REQ-FR-135 MUST. Система должна отображать дату и время пользователю в выбранном им часовом поясе.

REQ-FR-136 MUST. Система должна хранить и рассчитывать события так, чтобы исключить неоднозначность между часовыми поясами.

## 7.13. Продление выполняющейся сессии

REQ-FR-137 MUST. Если карточка находится в статусе «Выполняется» и плановое время окончания наступило, система должна автоматически продлить сессию.

REQ-FR-138 MUST. Автоматическое продление выполняющейся сессии должно выполняться на настраиваемый интервал.

REQ-FR-139 MUST. Интервал автоматического продления по умолчанию должен составлять 15 минут.

REQ-FR-140 MUST. Администратор должен иметь возможность изменить интервал автоматического продления в настройках системы.

REQ-FR-141 MUST. Система должна фиксировать каждое автоматическое продление в истории карточки и аудите.

REQ-FR-142 MUST. Если продление выполняющейся сессии создаёт коллизию с другим запланированным подключением этого же L2, система должна зафиксировать информацию о коллизии.

REQ-FR-143 MUST. Если продление выполняющейся сессии создаёт коллизию, система должна обработать её по правилам срочного подключения.

REQ-FR-144 MUST. При завершении карточки L2 должен иметь возможность указать фактическую продолжительность подключения.

REQ-FR-145 MUST. Фактическая продолжительность не должна заменять историю автоматических продлений и должна храниться как итоговое значение выполнения.

## 7.14. Метрики и отчёты

REQ-FR-146 MUST. Система должна предоставлять отчёт по количеству созданных карточек за период.

REQ-FR-147 MUST. Система должна предоставлять отчёт по количеству завершённых подключений за период.

REQ-FR-148 MUST. Система должна предоставлять отчёт по доле отклонённых карточек.

REQ-FR-149 MUST. Система должна предоставлять отчёт по доле повторно отклонённых карточек.

REQ-FR-150 MUST. Система должна предоставлять отчёт по просроченным карточкам.

REQ-FR-151 MAY. Система может рассчитывать среднее время назначения L2 как аналитический показатель после накопления достаточной истории карточек.

REQ-FR-152 MAY. Система может рассчитывать среднее время реакции L2 как аналитический показатель после накопления достаточной истории назначений и решений L2.

REQ-FR-153 MAY. Система может рассчитывать среднее время обработки L1 как аналитический показатель после накопления достаточной истории отклонённых и просроченных карточек.

REQ-FR-154 MUST. Система должна предоставлять отчёт по количеству срочных подключений и срочных коллизий.

REQ-FR-155 MUST. Система должна предоставлять отчёт по загрузке L2 по карточкам RDM.

## 7.15. Внерабочее время

REQ-FR-156 MUST. Система должна считать внерабочим подключением карточку, плановый интервал которой полностью или частично попадает на выходной день, праздничный день или время вне рабочего графика ответственного L2.

REQ-FR-157 MUST. Система должна позволять создавать внерабочие карточки только инженеру L2 для себя или руководителю.

REQ-FR-158 MUST. Создание внерабочей карточки не должно требовать отдельного подтверждения руководителя в RDM.

REQ-FR-159 MUST. Внерабочая карточка должна проходить тот же жизненный цикл и использовать те же уведомления, что и обычная карточка соответствующего типа.

REQ-FR-160 MUST. Система должна автоматически устанавливать отдельный признак внерабочего подключения, если выбранный интервал попадает на нерабочее время, выходной или праздничный день.

## 7.16. Клиентский часовой пояс

REQ-FR-161 MUST. Клиентский фрейм должен определять часовой пояс браузера клиента средствами frontend-приложения.

REQ-FR-162 MUST. При создании карточки через клиентский фрейм система должна показывать клиенту часовой пояс, в котором будет интерпретировано выбранное время.

REQ-FR-163 MUST. Клиент должен иметь возможность изменить часовой пояс в форме создания карточки, если автоматически определённый часовой пояс неверен.

REQ-FR-164 MUST. Backend RDM должен сохранять выбранный или автоматически определённый часовой пояс клиента вместе с карточкой на момент её создания.

REQ-FR-165 MUST. Внутренним пользователям RDM время карточки должно отображаться в часовом поясе соответствующего внутреннего пользователя, независимо от часового пояса клиента на момент создания.

# 8. Требования к интерфейсам

## 8.1. Общие требования

UI-001 MUST. Внутренний веб-интерфейс должен предоставлять список карточек с фильтрами по статусу, дате, клиенту, тикету, ответственному L2, сопровождающему L1, срочности, критичности и признаку просрочки.

UI-002 MUST. Интерфейс должен показывать текущий статус карточки.

UI-003 MUST. Интерфейс должен показывать плановое время начала, плановое время окончания и длительность в часовом поясе текущего пользователя.

UI-004 MUST. Интерфейс должен показывать базовое время в московском часовом поясе или давать возможность быстро его увидеть.

UI-005 MUST. Интерфейс должен скрывать или блокировать недоступные действия в зависимости от роли, статуса и бизнес-правил.

UI-006 MUST. При блокировке действия интерфейс должен показывать понятное объяснение причины.

UI-007 MUST. Интерфейс должен показывать историю изменений карточки внутренним пользователям с соответствующими правами.

UI-008 SHOULD. Интерфейс должен визуально выделять текущий статус карточки цветом фона: «Назначено» — голубой, «Подтверждено» — жёлтый, «Выполняется» — зелёный, «Отклонено» — красный, «Завершено» и «Отменено» — серый; срочные подключения должны выделяться красной рамкой, остальные признаки должны отображаться в заголовке или титуле карточки.

## 8.2. Интерфейс клиента во фрейме Omnidesk

UI-009 MUST. Клиентский фрейм должен отображать все карточки удалённого подключения, связанные с текущим тикетом Omnidesk.

UI-010 MUST. Клиентский фрейм должен позволять создать новую карточку только по текущему обращению Omnidesk, включая закрытое обращение, если backend RDM успешно переоткрыл его через Omnidesk API.

UI-011 MUST. Клиентский фрейм не должен позволять клиенту изменить дату, время или длительность существующей карточки.

UI-012 MUST. Клиентский фрейм не должен позволять клиенту отменить существующую карточку.

UI-013 MUST. Клиентский фрейм не должен показывать внутренние причины отказов L2.

UI-014 MUST. Клиентский фрейм не должен показывать глобальные очереди, графики сотрудников и внутренние данные RDM.

UI-015 MUST. В MVP клиентский интерфейс должен встраиваться в страницу обращения Omnidesk и сразу показывать список всех карточек RDM по текущему тикету, а также кнопку создания новой карточки, если создание разрешено бизнес-правилами.

UI-016 MUST. Клиентский интерфейс MVP должен получать номер текущего тикета из DOM страницы Omnidesk только как входной контекст для формы бронирования.

UI-017 MUST. Клиентский интерфейс MVP должен подтягивать имя, компанию и контактные данные из текущего тикета Omnidesk при их наличии и позволять клиенту актуализировать эти данные для создаваемой карточки.

UI-018 MUST. Клиентский интерфейс MVP должен показывать клиенту только данные карточек, которые backend RDM разрешил после серверной проверки тикета через Omnidesk API.

UI-019 MUST. Если клиенту требуется перенести или отменить подключение, клиентский фрейм должен показывать инструкцию написать сообщение в текущем тикете Omnidesk.

## 8.3. Интерфейс L1

UI-020 MUST. Интерфейс L1 должен позволять создавать карточки.

UI-021 MUST. Интерфейс L1 должен показывать назначенные ему отклонённые карточки.

UI-022 MUST. Интерфейс L1 должен показывать назначенные ему просроченные карточки.

UI-023 MUST. Интерфейс L1 должен позволять отметить клиента проинформированным о необходимости переноса.

UI-024 MUST. Интерфейс L1 должен позволять увеличить интервал собственных напоминаний по отклонённой карточке до 30 минут после информирования клиента.

UI-025 MUST. Интерфейс L1 должен позволять изменить дату, время и описание карточки после согласования с клиентом.

## 8.4. Интерфейс L2

UI-026 MUST. Интерфейс L2 должен показывать назначенные ему карточки.

UI-027 MUST. Интерфейс L2 должен позволять подтвердить назначение.

UI-028 MUST. Интерфейс L2 должен позволять отклонить назначение с причиной.

UI-029 MUST. Интерфейс L2 должен позволять начать выполнение.

UI-030 MUST. Интерфейс L2 должен позволять завершить выполнение с указанием перечня работ и результата.

UI-031 MUST. Интерфейс L2 должен позволять создать обычную, срочную или ретроспективную карточку только для себя.

UI-032 MUST. Интерфейс L2 должен позволять выбрать результат подключения из справочника и указать текстовый комментарий.

UI-033 MUST. Интерфейс L2 должен позволять указать фактическую продолжительность подключения при завершении карточки.

## 8.5. Интерфейс руководителя

UI-034 MUST. Интерфейс руководителя должен показывать карточки, требующие внимания руководителя.

UI-035 MUST. Интерфейс руководителя должен показывать карточки с первым полным отказом всех L2 или отсутствием кандидатов.

UI-036 MUST. Интерфейс руководителя должен показывать карточки с повторным неуспешным циклом и повышенной критичностью.

UI-037 MUST. Интерфейс руководителя должен позволять вручную назначить или переназначить L2.

UI-038 MUST. Интерфейс руководителя должен позволять отклонить назначение за инженера с указанием причины.

UI-039 MUST. Интерфейс руководителя должен позволять видеть сведения о коллизии срочного подключения.

UI-040 MUST. Интерфейс руководителя должен позволять принять решение о включении или исключении сотрудника из распределения.

## 8.6. Интерфейс администратора

UI-041 MUST. Интерфейс администратора должен позволять управлять пользователями и ролями.

UI-042 MUST. Интерфейс администратора должен позволять настраивать графики сотрудников.

UI-043 MUST. Интерфейс администратора должен позволять управлять участием сотрудников в распределении на основании решения руководителя.

UI-044 MUST. Интерфейс администратора должен позволять корректировать производственный календарь РФ.

UI-045 MUST. Интерфейс администратора должен позволять настраивать интеграции и шаблоны уведомлений.

UI-046 MUST. Интерфейс администратора должен позволять управлять справочником результатов подключения.

UI-047 MUST. Интерфейс администратора должен позволять настраивать интервал автоматического продления выполняющейся сессии.

## 8.7. Интерфейс отчётов

UI-048 SHOULD. Интерфейс должен предоставлять отчёты и метрики MVP по карточкам, отклонениям, просрочкам, реакции L2, обработке L1, срочным подключениям, срочным коллизиям и загрузке L2.

UI-049 MUST. При клике на карточку в клиентском фрейме система должна показывать клиенту полную доступную ему информацию по карточке.

UI-050 MUST. Клиентский фрейм должен запрещать создание новой карточки по текущему тикету, если по этому тикету уже существует карточка в статусе, отличном от «Завершено» и «Отменено».

UI-051 MUST. Форма создания карточки в клиентском фрейме должна показывать клиенту определённый часовой пояс и позволять изменить его перед созданием карточки.

# 9. Требования к API

## 9.1. Общие требования к API

API-001 MUST. Система должна предоставлять API для внутренних веб-интерфейсов.

API-002 MUST. Система должна предоставлять API для клиентского фрейма Omnidesk.

API-003 MUST. API должен выполнять проверку прав на стороне сервера для каждого изменяющего действия.

API-004 MUST. API должен возвращать диагностируемые ошибки при нарушении бизнес-правил.

API-005 MUST. API должен поддерживать идемпотентность для внешних событий и повторных запросов интеграций, где возможно повторение доставки.

API-006 SHOULD. API должен использовать единый формат ошибок.

API-007 SHOULD. API должен использовать версионирование.

## 9.2. Логические группы API

| Группа | Операции |
|---|---|
| Cards | Создание, чтение, изменение времени, отмена, подтверждение, отказ, начало, завершение; для клиентского фрейма доступны только чтение карточек текущего тикета и создание новой карточки по текущему тикету. |
| Assignments | Ручное назначение, переназначение, фиксация отказов, история назначений. |
| Calendar | Просмотр календаря, поиск доступного времени, проверка конфликтов. |
| Users | Пользователи, роли, часовые пояса, связи с внешними системами. |
| Schedules | Графики, отсутствия, производственный календарь. |
| Distribution | Очереди L1/L2, участие в распределении, позиция Round Robin. |
| Notifications | Настройки получателей, события, история доставки. |
| Integrations | Omnidesk, Telegram, Битрикс24, состояние синхронизации. |
| Audit | Журнал действий и изменений. |

## 9.3. Требования к ключевым операциям

API-008 MUST. Операция создания карточки должна принимать тикет, клиента, плановое время, длительность, описание, признак срочности и основание срочности при необходимости.

API-009 MUST. Операция создания карточки должна определять начальный статус по роли создателя и способу назначения.

API-010 MUST. Операция изменения времени должна принимать новое время, длительность и основание изменения, если оно требуется.

API-011 MUST. Операция отказа L2 должна принимать причину отказа.

API-012 MUST. Операция завершения должна принимать перечень выполненных работ, выбранный результат из справочника и комментарий инженера.

API-013 MUST. Операция отметки «Клиент проинформирован» должна фиксировать автора, время и канал информирования, если канал указан.

API-014 MUST. Операция ручного назначения L2 должна быть доступна только руководителю.

API-015 MUST. Операции администрирования распределения должны фиксировать основание или ссылку на решение руководителя.

API-016 MUST. Операция завершения карточки должна принимать выбранный результат из справочника результатов и текстовый комментарий.

API-017 MUST. Операция завершения карточки должна позволять передать фактическую продолжительность подключения.

API-018 MUST. API должен предоставлять операции управления справочником результатов подключения для администратора.

API-019 MUST. API должен предоставлять операции настройки интервала автоматического продления выполняющейся сессии.

API-020 MUST. API должен предоставлять endpoint для входящих событий Omnidesk, используемых для контроля расхождений и состояния тикета.

API-021 MUST. Входящие события Omnidesk должны обрабатываться идемпотентно.

API-022 MUST. Публичный API клиентского фрейма не должен предоставлять клиенту операции изменения даты, времени, длительности или отмены существующей карточки.

API-023 MUST. Публичный API клиентского фрейма должен предоставлять клиенту только операции чтения карточек текущего тикета и создания новой карточки по текущему тикету.

API-024 MUST. Операция создания карточки из клиентского фрейма должна принимать часовой пояс клиента, определённый браузером или выбранный клиентом вручную.

# 10. Требования к данным

## 10.1. Хранение времени

DATA-021 MUST. Система должна хранить временные значения в формате, позволяющем однозначно пересчитывать их между часовыми поясами.

DATA-022 MUST. Система должна использовать Europe/Moscow как основной бизнес-часовой пояс.

DATA-023 MUST. Система должна хранить выбранный часовой пояс пользователя для отображения.

DATA-024 MUST. Система должна корректно отображать время пользователям, работающим в часовом поясе Asia/Yekaterinburg.

DATA-025 MUST. Система должна проверять пересечения интервалов по нормализованным временным значениям.

## 10.2. Целостность

DATA-026 MUST. Система должна обеспечивать невозможность двух активных карточек с пересекающимся временем для одного L2.

DATA-027 MUST. Система должна обеспечивать атомарность операции назначения L2 и резервирования времени.

DATA-028 MUST. Система должна обеспечивать атомарность перехода статуса и записи истории.

DATA-029 MUST. Система должна сохранять историю назначений и отказов.

DATA-030 MUST. Система не должна удалять историю отказов при изменении времени, но должна начинать новый цикл назначения отдельно.

DATA-031 MUST. Система должна отличать отказ в одном цикле назначения от отказа в новом цикле после изменения времени.

## 10.3. Журналирование данных

DATA-032 MUST. Система должна хранить дату и автора создания карточки.

DATA-033 MUST. Система должна хранить дату и автора каждого изменения значимых полей.

DATA-034 MUST. Система должна хранить источник действия: клиентский фрейм, внутренний интерфейс, система, интеграция.

DATA-035 MUST. Система должна хранить результат попыток синхронизации с Omnidesk.

DATA-036 MUST. Система должна хранить результат попыток доставки уведомлений.

## 10.4. Справочник результатов и продления

DATA-037 MUST. Система должна хранить справочник результатов подключения в базе данных RDM.

DATA-038 MUST. Значения справочника результатов должны иметь признаки активности и порядка отображения.

DATA-039 MUST. Деактивация значения справочника результатов не должна изменять уже завершённые карточки.

DATA-040 MUST. Система должна хранить события автоматического продления сессии отдельно от итоговой фактической продолжительности.

DATA-041 MUST. Событие продления должно хранить прежнее плановое окончание, новое плановое окончание, интервал продления, время события и наличие коллизии.

## 10.5. Сроки хранения

DATA-042 MUST. Карточки удалённого подключения должны храниться бессрочно либо не менее 3 лет; окончательный режим выбирается настройкой хранения.

DATA-043 MUST. История карточки должна храниться не меньше срока хранения самой карточки.

DATA-044 MUST. Журнал аудита должен храниться не менее 3 лет.

DATA-045 MUST. Записи уведомлений должны храниться не менее 1 года.

DATA-046 MUST. Ошибки интеграций должны храниться не менее 1 года.

DATA-047 MUST. Технические логи приложения должны храниться не менее 90 дней.

DATA-048 MUST. Данные клиентского фрейма должны храниться в составе карточек, тикетных связей и аудита по соответствующим срокам хранения.

## 10.6. Внешние идентификаторы Omnidesk

DATA-049 MUST. Пользователь RDM, связанный с сотрудником Omnidesk, должен хранить `omnidesk_staff_id`.

DATA-050 MUST. Клиентская связь RDM должна хранить `omnidesk_user_id`, если карточка создана или отображается через тикет Omnidesk.

DATA-051 SHOULD. Клиентская связь RDM может хранить `omnidesk_company_id`, если компания доступна из Omnidesk и используется для фильтрации или отображения.

DATA-052 MUST. Связь карточки с тикетом должна хранить `omnidesk_case_id` и может хранить `omnidesk_case_number`.

## 10.7. Часовой пояс клиента

DATA-053 MUST. Карточка, созданная через клиентский фрейм, должна хранить часовой пояс клиента на момент создания.

DATA-054 MUST. Клиентская связь RDM может хранить последний подтверждённый часовой пояс клиента, связанный с `omnidesk_user_id`.

DATA-055 SHOULD. При повторном создании карточки клиентом система должна предлагать последний подтверждённый часовой пояс клиента, если он сохранён.

DATA-056 MUST. Если часовой пояс клиента не удалось определить автоматически и клиент не выбрал его вручную, система должна использовать значение по умолчанию Europe/Moscow и явно показать это клиенту перед созданием карточки.

# 11. Интеграция с Omnidesk

## 11.1. Назначение интеграции

INT-001 MUST. Omnidesk должен оставаться основной системой ведения обращений клиента.

INT-002 MUST. RDM должен быть источником истины по карточке удалённого подключения, расписанию и состоянию жизненного цикла.

INT-003 MUST. Система должна связывать карточку RDM с тикетом Omnidesk.

INT-004 MUST. Система должна поддерживать клиентский фрейм в личном кабинете Omnidesk.

INT-005 MUST. Интеграция должна использовать статусы обращения Omnidesk «Открытое», «В ожидании» и «Закрытое», соответствующие API-значениям `open`, `waiting` и `closed`.

INT-006 MUST. RDM не должен закрывать обращение Omnidesk после завершения карточки удалённого подключения.

## 11.2. Границы ответственности RDM и Omnidesk

INT-007 MUST. Роли L1, L2, руководителя, администратора, участие в распределении, графики, доступность и очереди Round Robin должны определяться только настройками RDM.

INT-008 MUST. Система не должна использовать группы Omnidesk как источник ролей RDM, прав доступа, участия в распределении или доступности сотрудников.

INT-009 MUST. Система не должна изменять группу обращения Omnidesk при назначении L1 или L2.

INT-010 MUST. Система должна использовать Omnidesk-группы только как внешнюю справочную информацию, если они получены из тикета.

INT-011 MUST. Руководитель не должен назначаться ответственным сотрудником в Omnidesk в рамках процесса RDM.

## 11.3. Исходящая синхронизация в Omnidesk

INT-012 MUST. При создании карточки система должна добавить в Omnidesk внутреннюю заметку со ссылкой на карточку RDM, временем подключения и кратким описанием.

INT-013 MUST. При назначении или смене ответственного L2 система должна обновлять ответственного сотрудника в Omnidesk.

INT-014 MUST. При переходе в «Отклонено» система должна добавить внутреннюю заметку о невозможности назначения на выбранное время.

INT-015 MUST. При назначении сопровождающего L1 система должна обновить ответственного сотрудника в Omnidesk на выбранного L1.

INT-016 MUST. При отмене карточки система должна добавить в Omnidesk внутреннюю заметку об отмене.

INT-017 MUST. При завершении карточки система должна добавить в Omnidesk внутреннюю заметку с перечнем выполненных работ, выбранным результатом и комментарием инженера.

INT-018 MUST. Инженер должен самостоятельно отправлять клиенту публичное сообщение по результатам подключения из Omnidesk, если такое сообщение требуется процессом поддержки.

INT-019 SHOULD. RDM может формировать внутреннюю заметку или шаблонный текст для инженера, но не должен автоматически отправлять клиенту публичный ответ по результатам подключения без действия инженера.

INT-020 MUST. RDM должен автоматически отправлять клиенту через тикет Omnidesk уведомление перед подключением за 15 минут до начала подтверждённой карточки.

INT-021 MUST. Клиентское уведомление перед подключением должно отправляться только для карточек в статусе «Подтверждено».

INT-022 MUST. Текст клиентского уведомления перед подключением должен формироваться по настраиваемому шаблону.

INT-023 SHOULD. При ошибке синхронизации система должна сохранять состояние расхождения и ставить событие в очередь повторной доставки.

## 11.4. Кастомные поля Omnidesk

INT-024 SHOULD. RDM может использовать обращенческие кастомные поля Omnidesk только для справочной или поисковой информации по тикету, но не как обязательное хранилище состояния карточек.

INT-025 MUST. Система не должна хранить состояние конкретной карточки только в кастомных полях Omnidesk, так как в рамках одного тикета может существовать несколько подключений.

INT-026 MAY. Для MVP допускается не создавать кастомные поля Omnidesk под RDM и ограничиться ответственным сотрудником, внутренними заметками и ссылками на карточки RDM.

## 11.5. Клиентский фрейм

INT-027 MUST. Для MVP клиентский интерфейс должен использовать текущую схему встраивания в Omnidesk: JS/фрейм размещается на странице конкретного обращения, получает номер текущего тикета из URL вида `/user/cases/record/{case_number}/` и внутренний `case_id` из DOM-контекста страницы. Оба значения считаются непроверенным вводом и используются только для серверной проверки.

INT-028 MUST. Клиентский фрейм должен запрещать доступ к карточкам других тикетов и других клиентов.

INT-029 MUST. Операции клиента во фрейме должны проходить те же серверные проверки, что и операции внутренних пользователей.

INT-030 MUST. RDM не должен считать номер тикета или `case_id`, полученные из URL/DOM страницы Omnidesk, доказательством личности клиента или права доступа к карточке.

INT-031 MUST. После получения номера тикета и `case_id` из клиентского интерфейса backend RDM должен получить тикет через Omnidesk API по `case_id`, сверить возвращённый `case_number` с переданным номером и проверить, что тикет существует, не удалён и не находится в спаме.

INT-032 MUST. Если клиент создаёт карточку из тикета Omnidesk в статусе «Закрытое», backend RDM должен перед созданием карточки перевести тикет по подтверждённому `case_id` в «Открытое» через Omnidesk API и повторно получить его, чтобы подтвердить статус «Открытое».

INT-033 MUST. Если переоткрытие закрытого тикета Omnidesk завершилось ошибкой, RDM должен отказать в создании карточки и показать клиенту понятное сообщение о невозможности записи по этому обращению.

INT-034 MUST. Backend RDM должен использовать `user_id` тикета Omnidesk как идентификатор клиента для связи карточки с обращением.

INT-035 SHOULD. Если в MVP RDM не получает доверенную идентичность браузерной сессии клиента, система должна считать авторизацию клиента выполненной на стороне личного кабинета Omnidesk для просмотра текущего тикета, но всё равно ограничивать операции RDM контекстом этого тикета и серверными проверками через Omnidesk API.

INT-036 MAY. В следующих версиях может быть добавлен SSO/JWT или другой доверенный серверный механизм авторизации клиентского фрейма, если Omnidesk предоставит подходящий официальный контракт или это потребуется по требованиям безопасности.

INT-037 MUST. Публичный API клиентского фрейма должен отдавать карточки только по паре текущих `case_id` и номера тикета после серверной проверки тикета через Omnidesk API.

INT-038 MUST. Ответ публичного API клиентского фрейма должен содержать только данные карточек, доступные клиенту: статус, плановое время, длительность, описание, доступные действия чтения и публичные комментарии, если они предусмотрены процессом.

INT-039 MUST. Публичный API клиентского фрейма не должен отдавать внутренние причины отказов L2, данные распределения, графики сотрудников, внутренние идентификаторы пользователей RDM и технические журналы.

INT-040 SHOULD. Публичный API клиентского фрейма должен использовать ограничения CORS/Origin для домена личного кабинета Omnidesk, rate limit и короткоживущую frame-session RDM, привязанную к подтверждённой паре `case_id` и номера тикета. Если Origin или Referer передан браузером, последующие запросы по этой session должны совпадать с сохранённым источником.

INT-041 MUST. Публичный API клиентского фрейма не должен предоставлять клиенту операции переноса или отмены карточек.

## 11.6. Входящие события Omnidesk

INT-042 MUST. Система должна принимать входящее событие Omnidesk о ручной смене ответственного в связанном тикете.

INT-043 MUST. При ручной смене ответственного в Omnidesk система должна уведомить L2, который должен подключаться по карточке RDM, и зафиксировать расхождение.

INT-044 MUST. Ручная смена ответственного в Omnidesk не должна автоматически переназначать карточку RDM.

INT-045 MUST. После ручной смены ответственного в Omnidesk дальнейшая корректировка должна выполняться вручную: вернуть ответственного в тикете Omnidesk или назначить нового ответственного для подключения в RDM.

INT-046 MUST. Система должна принимать входящее событие Omnidesk о переносе связанного тикета в корзину или спам.

INT-047 MUST. Если связанный тикет Omnidesk удалён или перенесён в спам при наличии незавершённой карточки, система должна уведомить L1 и руководителя.

## 11.7. Детали интеграционного контракта MVP

Для MVP фиксируются следующие решения:

- отдельная авторизация клиента в RDM не используется;
- авторизация клиента считается выполненной в Omnidesk для просмотра текущего тикета, но RDM дополнительно ограничивает все операции контекстом этого тикета;
- RDM получает `case_number` из URL страницы и `case_id` из DOM-контекста, затем читает обращение по `case_id` и серверно сверяет оба значения;
- RDM может подтягивать из Omnidesk тип обращения, категорию обращения и другие поля тикета, если они доступны через API или `custom_fields`;
- внутренние заметки и клиентские уведомления формируются по настраиваемым шаблонам RDM;
- при недоступности Omnidesk RDM продолжает работать как отдельная система, но сообщает пользователю об ошибке интеграции и ставит внешнюю синхронизацию в повторную обработку;
- RDM учитывает официальные лимиты Omnidesk API и заголовки ограничения частоты запросов;
- RDM фиксирует результат подключения во внутренней заметке Omnidesk и в полях карточки RDM;
- базовая защита клиентского фрейма MVP включает серверную проверку тикета, минимальный состав отдаваемых данных, ограничения CORS/Origin, rate limit, короткоживущую frame-session, аудит операций и запрет передачи внутренних данных клиенту.

## 11.8. Read-only инвентаризация рабочего Omnidesk API

Инвентаризация выполнена 2026-08-28 с использованием локального API-ключа в режиме только чтения. Секреты, персональные данные, содержимое тикетов и имена сотрудников в документ не включаются.

INT-048 MUST. RDM должен учитывать, что в рабочем аккаунте Omnidesk API возвращает обращения, сотрудников, группы, пользователей, компании, метки, фильтры, кастомные поля, сообщения тикета и историю действий тикета.

INT-049 MUST. Для связи карточки с обращением RDM может использовать поля Omnidesk `case_id`, `case_number`, `user_id`, `staff_id`, `group_id`, `status`, `priority`, `channel`, `created_at`, `updated_at`, `closed_at`, `last_response_at`, `deleted`, `spam`, `custom_fields`, `labels` и `locked_labels`.

INT-050 SHOULD. RDM может использовать тип обращения и категорию обращения Omnidesk для предварительного заполнения карточки, фильтрации, отображения контекста и будущей аналитики, если эти данные доступны через поля тикета или `custom_fields`.

INT-051 MUST. Для назначения ответственного в Omnidesk RDM должен использовать `staff_id`, полученный из справочника сотрудников Omnidesk и сопоставленный с пользователем RDM в настройках RDM.

INT-052 MUST. RDM может использовать данные сотрудника Omnidesk `staff_id`, `staff_email`, `staff_full_name`, `active`, `status_id`, `role_id`, `staff_access_level` и `staff_working_hours` для справочного отображения и настройки сопоставления, но не как источник ролей, графиков или доступности RDM.

INT-053 MUST. Для проверки принадлежности тикета клиенту RDM может использовать `user_id` обращения Omnidesk и данные пользователя Omnidesk, включая `user_id`, `user_email`, `user_full_name`, `company_name`, `active`, `deleted`, `confirmed`, `type` и `custom_fields`.

INT-054 SHOULD. RDM может использовать данные компании Omnidesk, включая `company_id`, `company_name`, `company_group_id`, `company_domains`, `active` и `deleted`, как дополнительный тикетный контекст и для фильтрации клиентского доступа.

INT-055 SHOULD. RDM может использовать сообщения тикета Omnidesk для чтения истории коммуникации и отличать внутренние заметки от публичных сообщений по признаку `note`.

INT-056 MUST. Для фиксации результата подключения RDM должен создавать внутреннюю заметку Omnidesk, а не полагаться на кастомные поля обращения.

INT-057 MUST. Для контроля ручных внешних изменений RDM может использовать историю действий Omnidesk, где доступны `event`, `old_value`, `value`, `done_by` и `created_at`.

INT-058 SHOULD. RDM должен учитывать официальный лимит API Omnidesk, читать заголовки `rate_limit_per_minute`, `api_calls_left` и `retry_after`, а также учитывать, что запросы POST, PUT и DELETE засчитываются как два запроса в рамках лимита.

INT-059 SHOULD. При наличии нескольких карточек RDM в одном тикете Omnidesk основным способом отображения истории RDM в Omnidesk должны быть внутренние заметки со ссылками на конкретные карточки RDM.

NOTIF-016 MUST. Эскалация руководителю по L1 должна повторяться каждые 30 минут до отметки «Клиент проинформирован».

NOTIF-020 MUST. Система должна автоматически отправлять клиенту уведомление перед подключением через тикет Omnidesk за 15 минут до планового начала.

NOTIF-023 MUST. Клиентское уведомление перед подключением должно отправляться только для карточек в статусе «Подтверждено».

NOTIF-024 MUST. Текст клиентского уведомления перед подключением должен формироваться по настраиваемому шаблону.

NOTIF-025 MUST. Система не должна отправлять клиентское уведомление перед подключением для карточек в статусах «Создано», «Назначено», «Отклонено», «Выполняется», «Завершено» и «Отменено».

ADM-003 MUST. Система должна позволять администратору связывать пользователей с учётными записями Omnidesk, Telegram и Битрикс24.

ADM-004 MUST. Система должна позволять администратору настраивать рабочие графики сотрудников.

ADM-009 MUST. Система должна хранить аудит включения и исключения сотрудника из распределения.

ADM-010 MUST. Система должна позволять администратору настраивать параметры планирования: минимальное время до подключения, длительность по умолчанию, минимальную и максимальную длительность, горизонт планирования.

ADM-011 MUST. Система должна позволять администратору настраивать параметры уведомлений и шаблоны.

ADM-012 MUST. Система должна позволять администратору настраивать параметры интеграции с Omnidesk.

ADM-013 MUST. Система должна позволять администратору настраивать Telegram-бота и бота Битрикс24.

ADM-014 MUST. Система должна позволять администратору создавать, редактировать, деактивировать и упорядочивать значения справочника результатов подключения.

ADM-015 MUST. Система должна позволять администратору настраивать интервал автоматического продления выполняющейся сессии.

ADM-016 MUST. Система должна позволять администратору настраивать шаблон клиентского уведомления перед подключением.

# 14. Нефункциональные требования

## 14.1. Доступность и надёжность

NFR-001 SHOULD. Система должна быть доступна внутренним пользователям в рабочее время поддержки.

NFR-002 SHOULD. Планировщик автоматических задач должен устойчиво обрабатывать перезапуск приложения без потери напоминаний и ожидающих событий.

NFR-003 MUST. Система не должна терять карточку при временной недоступности Omnidesk, Telegram или Битрикс24.

NFR-004 MUST. Система должна сохранять изменяющее действие до запуска внешней синхронизации, если действие допустимо по бизнес-правилам.

## 14.2. Производительность

NFR-005 SHOULD. Открытие списка карточек за обычный период должно выполняться за приемлемое для операционной работы время.

NFR-006 SHOULD. Автоматическое назначение L2 должно выполняться без заметной задержки для пользователя после создания карточки.

NFR-007 SHOULD. Проверка конфликтов расписания должна выполняться достаточно быстро для интерактивного изменения времени.

Конкретные численные показатели производительности должны быть утверждены после оценки ожидаемого количества пользователей, карточек и интеграционных событий.

## 14.3. Масштабируемость

NFR-008 SHOULD. Система должна поддерживать рост количества сотрудников, клиентов и карточек без изменения базовой модели данных.

NFR-009 SHOULD. Очереди уведомлений и интеграционных событий должны быть отделены от пользовательских запросов.

## 14.4. Сопровождаемость

NFR-010 MUST. Бизнес-правила статусов, распределения и уведомлений должны быть покрыты автоматическими тестами.

NFR-011 SHOULD. Логика распределения L1 и L2 должна быть выделена так, чтобы её можно было тестировать отдельно от интерфейса.

NFR-012 SHOULD. Интеграции должны иметь диагностируемые состояния и журналы.

## 14.5. Локализация и время

NFR-013 MUST. Основной интерфейс MVP должен быть на русском языке.

NFR-014 MUST. Система должна поддерживать отображение времени в выбранном часовом поясе пользователя.

NFR-015 MUST. Система должна исключать двусмысленность при отображении и сохранении времени.

## 14.6. Архитектурные решения MVP

NFR-016 MUST. Backend MVP должен быть реализован на FastAPI.

NFR-017 MUST. Frontend MVP должен быть реализован на Vue 3 с использованием Vite.

NFR-018 MUST. Внутренние пользователи MVP должны авторизоваться через локальные учётные записи RDM.

NFR-019 MUST. Фоновые задачи MVP должны выполняться через Celery.

NFR-020 MUST. Redis должен использоваться как технический брокер фоновых задач Celery.

NFR-021 MUST. Бизнес-события, влияющие на состояние карточек и внешнюю синхронизацию, должны фиксироваться в PostgreSQL по паттерну outbox до передачи в фоновые обработчики.

NFR-022 MUST. Окружения MVP должны включать dev, stage и prod.

NFR-023 SHOULD. Dev, stage и prod должны разворачиваться через Docker Compose с разделением конфигурации окружений.

NFR-024 MUST. Резервное копирование MVP должно включать регулярный backup PostgreSQL.

NFR-025 SHOULD. При переводе RDM в критичный производственный контур резервное копирование PostgreSQL должно быть расширено до WAL/PITR.

NFR-026 MUST. Мониторинг MVP должен включать Prometheus и Grafana для метрик.

NFR-027 SHOULD. Ошибки приложения должны отправляться в Sentry или совместимый инструмент контроля ошибок.

NFR-028 MUST. MVP должен поддерживать актуальные версии Chrome, Edge и Safari.

NFR-029 SHOULD. Firefox должен поддерживаться в режиме best effort.

# 15. Безопасность и аудит

## 15.1. Авторизация

SEC-001 MUST. Все изменяющие операции должны проверять права пользователя на сервере.

SEC-002 MUST. В MVP клиентский фрейм должен использовать текущую схему встраивания в Omnidesk с серверной проверкой тикета через Omnidesk API.

SEC-003 MUST. Пользователь не должен иметь доступ к карточкам, не входящим в область его полномочий.

SEC-004 MUST. Система не должна хранить секреты интеграций в открытом виде.

SEC-005 MUST. Система должна разграничивать клиентские и внутренние данные.

SEC-006 MUST. Система должна проверять принадлежность тикета клиенту на сервере RDM перед показом или изменением карточки через клиентский фрейм.

SEC-007 MUST. Система не должна использовать cookies браузерной сессии Omnidesk как единственный механизм авторизации RDM, если Omnidesk не предоставляет для этого официальный доверенный контракт.

SEC-008 MUST. Любые значения, полученные клиентским JS из DOM страницы Omnidesk, должны считаться непроверенными входными данными и повторно проверяться backend RDM.

## 15.2. Аудит

AUD-001 MUST. Система должна фиксировать создание карточки.

AUD-002 MUST. Система должна фиксировать изменение статуса карточки.

AUD-003 MUST. Система должна фиксировать изменение даты, времени и длительности.

AUD-004 MUST. Система должна фиксировать назначение и переназначение L2.

AUD-005 MUST. Система должна фиксировать отказ L2 и причину отказа.

AUD-006 MUST. Система должна фиксировать отказ, выполненный руководителем за инженера.

AUD-007 MUST. Система должна фиксировать назначение сопровождающего L1.

AUD-008 MUST. Система должна фиксировать отметку L1 «Клиент проинформирован».

AUD-009 MUST. Система должна фиксировать срочные коллизии.

AUD-010 MUST. Система должна фиксировать завершение карточки и результат работ.

AUD-011 MUST. Система должна фиксировать административные изменения ролей, графиков, распределения, календаря и интеграций.

AUD-012 MUST. Запись аудита должна содержать автора, время, источник действия, объект, тип действия и существенные изменения.

AUD-013 MUST. Система должна фиксировать автоматическое продление выполняющейся сессии и коллизии, возникшие из-за продления.

AUD-014 MUST. Система должна фиксировать изменения справочника результатов подключения.

# 16. Ошибки и исключительные ситуации

ERR-001 MUST. Если при создании карточки указано недопустимое время, система должна отказать в создании и показать причину.

ERR-002 MUST. Если нет допустимых L2 при первичном распределении, система должна перевести карточку в «Отклонено», назначить L1 при наличии доступного L1 и уведомить руководителя.

ERR-003 MUST. Если все L2 отказались, система должна перевести карточку в «Отклонено», назначить L1 при наличии доступного L1 и уведомить руководителя.

ERR-004 MUST. Если нет доступных L1 для сопровождения, система должна оставить карточку без сопровождающего L1 и уведомить руководителя.

ERR-005 MUST. Если L2 не ответил до окончания планового интервала, система должна установить признак просрочки, остановить напоминания L2 и уведомить L1 и руководителя.

ERR-006 MUST. Если Omnidesk недоступен, система должна сохранить карточку или изменение в RDM и зафиксировать ошибку синхронизации.

ERR-007 MUST. Если Telegram или Битрикс24 недоступен, система должна зафиксировать ошибку доставки уведомления.

ERR-008 MUST. Если пользователь пытается выполнить действие в недопустимом статусе, система должна отказать и вернуть диагностируемую ошибку.

ERR-009 MUST. Если клиент пытается получить чужую карточку, система должна отказать в доступе.

ERR-010 MUST. Если при ручном назначении L2 возникает пересечение с другой карточкой, система должна отказать либо потребовать отдельного сценария срочного конфликта, если действие относится к срочному подключению.

ERR-011 MUST. Если автоматическое продление выполняющейся сессии создаёт коллизию, система должна зафиксировать коллизию и запустить обработку по правилам срочного подключения.

ERR-012 MUST. Если Omnidesk сообщает о ручной смене ответственного в связанном тикете, система должна зафиксировать расхождение и уведомить L2, но не должна автоматически менять ответственного в карточке RDM.

ERR-013 MUST. Если Omnidesk сообщает о переносе связанного тикета в корзину или спам, система должна уведомить L1 и руководителя при наличии незавершённой карточки.

# 17. Критерии приемки

AC-001 MUST. Клиент видит во фрейме Omnidesk все карточки RDM по текущему тикету и может создать новую карточку только по этому же тикету, если создание разрешено бизнес-правилами.

AC-002 MUST. Карточка клиента или L1 сначала получает статус «Создано», затем автоматически переходит в «Назначено» при найденном L2.

AC-003 MUST. В статусе «Создано» нельзя изменить время или отменить карточку.

AC-004 MUST. Если при первичном распределении нет доступных L2, карточка переходит в «Отклонено», уведомляются L1 и руководитель.

AC-005 MUST. Если один L2 отклонил карточку, карточка остаётся в «Назначено» и назначается следующему L2.

AC-006 MUST. Если все доступные L2 отклонили карточку, карточка переходит в «Отклонено».

AC-007 MUST. Руководитель получает уведомление уже после первого полного круга отказов или отсутствия кандидатов.

AC-008 MUST. Повторный неуспешный цикл повышает критичность карточки.

AC-009 MUST. L1 получает напоминания каждые 10 минут по отклонённой карточке до нового времени или отмены.

AC-010 MUST. После второго напоминания L1 без отметки информирования клиента руководитель получает уведомление.

AC-011 MUST. После отметки «Клиент проинформирован» L1 может увеличить собственный интервал напоминаний до 30 минут.

AC-012 MUST. L2, не ответивший на назначение, получает напоминания каждые 10 минут до окончания планового интервала.

AC-013 MUST. Отсутствие ответа L2 не считается отказом.

AC-014 MUST. После окончания планового интервала без решения L2 карточка остаётся «Назначено» и получает признак просрочки.

AC-015 MUST. Нельзя назначить одному L2 два пересекающихся удалённых подключения.

AC-016 MUST. L2 может создать карточку только для себя.

AC-017 MUST. L2 может создать ретроспективную карточку, и если подключение завершено, система требует работы и результат.

AC-018 MUST. Руководитель может создать карточку с конкретным L2 или с вариантом «Автоматически».

AC-019 MUST. Клиент не может переносить или отменять карточку через клиентский фрейм RDM; для переноса или отмены клиент пишет сообщение в текущем тикете Omnidesk, после чего изменение выполняет сотрудник.

AC-020 MUST. При срочном конфликте фиксируется коллизия, уведомляются руководитель, L1 и L2, а переназначение запускается автоматически.

AC-021 MUST. Завершение карточки невозможно без перечня выполненных работ и результата.

AC-022 MUST. Все ключевые изменения карточки видны в истории и журнале аудита.

AC-023 MUST. Время отображается пользователям в выбранном часовом поясе, при этом основной бизнес-часовой пояс системы Europe/Moscow.

AC-024 MUST. Выходные и праздничные дни учитываются по производственному календарю РФ с возможностью корректировки.

AC-025 MUST. Интеграционные ошибки Omnidesk не приводят к потере карточки RDM.

AC-026 MUST. RDM не меняет группу обращения Omnidesk при назначении L1 или L2.

AC-027 MUST. При назначении L2 в RDM ответственный сотрудник в Omnidesk обновляется на этого L2.

AC-028 MUST. При завершении подключения RDM добавляет внутреннюю заметку в Omnidesk и не закрывает обращение.

AC-029 MUST. Результат подключения выбирается из администрируемого справочника, и инженер может добавить комментарий.

AC-030 MUST. При ручной смене ответственного в Omnidesk RDM уведомляет L2 по карточке и фиксирует расхождение без автоматического переназначения карточки.

AC-031 MUST. Если связанный тикет Omnidesk удалён или перенесён в спам, RDM уведомляет L1 и руководителя при наличии незавершённой карточки.

AC-032 MUST. Активная сессия автоматически продлевается на 15 минут по умолчанию, если наступило плановое окончание, а карточка всё ещё в статусе «Выполняется».

AC-033 MUST. Коллизия из-за автоматического продления фиксируется и обрабатывается по правилам срочного подключения.

AC-034 MUST. Система предоставляет обязательные MVP-отчёты по карточкам, отклонениям, повторным отклонениям, просрочкам, срочным подключениям, срочным коллизиям и загрузке L2; средние времена назначения, реакции L2 и обработки L1 могут быть добавлены как аналитические показатели после накопления истории.

AC-035 MUST. Система применяет согласованные сроки хранения карточек, истории, аудита, уведомлений, ошибок интеграций и технических логов.

AC-036 MUST. Система автоматически отправляет клиенту уведомление через тикет Omnidesk за 15 минут до начала подтверждённой карточки.

AC-037 MUST. Система не отправляет клиентское уведомление перед подключением для карточек, которые не находятся в статусе «Подтверждено».

AC-038 MUST. Клиентское уведомление перед подключением формируется по шаблону, настраиваемому администратором.

AC-039 MUST. RDM позволяет сопоставить внутреннего пользователя с сотрудником Omnidesk по `staff_id`.

AC-040 MUST. RDM использует `user_id` обращения Omnidesk для серверной проверки принадлежности тикета клиенту.

AC-041 MUST. RDM отличает внутреннюю заметку Omnidesk от публичного сообщения по признаку `note` при чтении сообщений тикета.

AC-042 MUST. Клиентский интерфейс RDM встраивается в страницу обращения Omnidesk и открывается из кнопки бронирования.

AC-043 MUST. Номер тикета, полученный из URL или DOM страницы Omnidesk, используется только как контекст формы и проходит серверную проверку через Omnidesk API.

AC-044 MUST. Backend RDM отказывает в создании, переносе или отмене карточки, если тикет Omnidesk не найден, удалён или находится в спаме.

AC-045 MUST. Если клиент создаёт карточку из закрытого тикета Omnidesk, RDM сначала переводит статус тикета из «Закрытое» в «Открытое» через Omnidesk API и только после этого создаёт карточку подключения.

AC-046 MUST. При создании карточки на выходной, праздничный день или вне рабочего графика RDM разрешает действие только L2 для себя или руководителю, не требует отдельного подтверждения руководителя и устанавливает признак внерабочего подключения.

AC-047 MUST. Клиентский фрейм не позволяет создать новую карточку по текущему тикету, если по этому тикету уже есть карточка в статусе, отличном от «Завершено» и «Отменено».

AC-048 MUST. Публичный API клиентского фрейма отдаёт только минимально допустимые клиентские данные карточек по текущему тикету и не раскрывает внутренние данные RDM.

AC-049 MUST. Публичный API клиентского фрейма не предоставляет операций изменения даты, времени, длительности или отмены существующей карточки.

AC-050 MUST. При создании карточки из клиентского фрейма RDM определяет часовой пояс браузера клиента, показывает его клиенту, позволяет изменить перед созданием и сохраняет выбранный часовой пояс в карточке.

# 20. Приложения

## Приложение А. Сценарии использования

### UC-001. Клиент создаёт обычное подключение

1. Клиент открывает фрейм RDM в личном кабинете Omnidesk.
2. Система определяет номер текущего тикета из контекста страницы Omnidesk.
3. Система показывает все карточки RDM, связанные с текущим тикетом.
4. Если по тикету нет активной карточки, клиент нажимает кнопку создания новой карточки.
5. Система подтягивает данные из тикета, определяет часовой пояс браузера клиента и показывает его в форме.
6. Клиент указывает дату, время, длительность, описание, при необходимости актуализирует контактные данные и часовой пояс.
7. Система проверяет правила планирования.
8. Система создаёт карточку в статусе «Создано».
9. Система запускает автоматическое назначение L2.
10. Если L2 найден, система переводит карточку в «Назначено».
11. Если L2 не найден, система переводит карточку в «Отклонено» и запускает сопровождение L1.

### UC-002. L1 создаёт карточку после общения с клиентом

1. L1 открывает форму создания карточки.
2. L1 выбирает клиента, тикет, дату, время, длительность и описание.
3. Система проверяет правила планирования.
4. Система создаёт карточку в статусе «Создано».
5. Система запускает автоматическое назначение L2.

### UC-003. Руководитель создаёт карточку с конкретным L2

1. Руководитель открывает форму создания карточки.
2. Руководитель выбирает клиента, тикет, время и конкретного L2.
3. Система проверяет полномочия и конфликт расписания.
4. Система создаёт карточку в статусе «Назначено».
5. Система уведомляет L2.

### UC-004. Руководитель создаёт карточку с автоматическим назначением

1. Руководитель открывает форму создания карточки.
2. Руководитель выбирает значение «Автоматически» в поле ответственного.
3. Система создаёт карточку в статусе «Создано».
4. Система запускает автоматическое назначение L2.

### UC-005. L2 создаёт карточку для себя

1. L2 открывает форму создания карточки.
2. Система ограничивает выбор ответственного текущим L2.
3. L2 указывает время, длительность и описание.
4. Система создаёт карточку в статусе «Назначено».

### UC-006. L2 отклоняет назначение

1. L2 открывает назначенную карточку.
2. L2 выбирает действие «Отклонить».
3. Система требует причину отказа.
4. Система сохраняет отказ.
5. Система ищет следующего допустимого L2.
6. Если следующий L2 найден, система назначает его и оставляет карточку в «Назначено».
7. Если следующий L2 не найден, система переводит карточку в «Отклонено».

### UC-007. L1 обрабатывает отклонённую карточку

1. Система назначает сопровождающего L1.
2. L1 получает уведомление.
3. L1 связывается с клиентом.
4. L1 отмечает клиента проинформированным.
5. L1 согласовывает новое время.
6. L1 меняет время карточки.
7. Система запускает новый цикл назначения L2.

### UC-008. Клиент переносит отклонённую карточку самостоятельно

1. Клиент открывает фрейм Omnidesk.
2. Клиент выбирает карточку в статусе «Отклонено».
3. Клиент указывает новое время.
4. Система проверяет правила планирования.
5. Система закрывает задачу L1 по согласованию нового времени.
6. Система запускает новый цикл назначения L2.

### UC-009. L2 не отвечает на назначение

1. Система назначает L2.
2. L2 не подтверждает и не отклоняет карточку.
3. Система отправляет напоминания каждые 10 минут.
4. На втором напоминании система уведомляет руководителя.
5. После окончания планового интервала система прекращает напоминания L2.
6. Система оставляет статус «Назначено» и ставит признак просрочки.
7. Система назначает L1 и уведомляет L1 и руководителя.

### UC-010. Срочное подключение создаёт конфликт

1. Создаётся срочная карточка.
2. Система обнаруживает конфликт с плановой карточкой.
3. Система фиксирует коллизию.
4. Система уведомляет руководителя, L1 и затронутого L2.
5. Система автоматически запускает переназначение плановой карточки.
6. Если новый L2 найден, плановая карточка остаётся «Назначено».
7. Если все L2 отказались, плановая карточка переходит в «Отклонено».

### UC-011. L2 завершает подключение

1. L2 открывает карточку в статусе «Выполняется».
2. L2 выбирает завершение.
3. Система требует перечень выполненных работ.
4. Система требует выбрать результат из справочника.
5. Система позволяет указать комментарий и фактическую продолжительность.
6. Система фиксирует фактическое окончание.
7. Система переводит карточку в «Завершено».
8. Система добавляет внутреннюю заметку с результатом в Omnidesk.

### UC-012. Выполняющаяся сессия продлевается

1. L2 начал подключение, карточка находится в статусе «Выполняется».
2. Наступает плановое время окончания.
3. Система автоматически продлевает сессию на настроенный интервал.
4. Система фиксирует продление в истории и аудите.
5. Если продление создаёт коллизию, система фиксирует коллизию.
6. Система обрабатывает коллизию по правилам срочного подключения.

## Приложение Б. Проверочные правила статусов

| Проверка | Ожидаемый результат |
|---|---|
| Изменить время в «Создано» | Запрещено. |
| Отменить в «Создано» | Запрещено. |
| Отказ одного L2 | Статус остаётся «Назначено». |
| Отказ всех L2 | Статус «Отклонено». |
| Нет кандидатов L2 | Статус «Отклонено». |
| Повторный полный отказ | «Отклонено», критичность повышена. |
| Нет ответа L2 до конца интервала | «Назначено» плюс признак просрочки. |
| Перенос клиентом в «Отклонено» | Новый цикл назначения L2. |
| Завершение без результата | Запрещено. |
| Клиентская отмена в «Выполняется» | Запрещено. |
