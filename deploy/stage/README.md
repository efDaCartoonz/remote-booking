# RDM — Руководство по тестовому стенду (Raspberry Pi 5 / ARM64)

## 1. Цель и границы стенда

Тестовый стенд RDM предназначен для ручной проверки релизов и сценариев работы приложения владельцем/инженером на аппаратной платформе Raspberry Pi 5 (архитектура ARM64 / aarch64).

**Границы стенда:**
- **Не является production-контуром:** стенд предназначен исключительно для верификации кандидатов в релиз и проведения управляемых smoke-проверок.
- **Отсутствие реальных персональных данных:** база данных стенда изначально пуста; тестирование выполняется на синтетических карточках и пользователях.
- **Внешние отправки отключены по умолчанию тремя флагами:** `NOTIFICATION_DELIVERY_ENABLED=false` (Telegram и Битрикс24), `REMINDER_SCANNER_ENABLED=false` (напоминания) и `OMNIDESK_OUTBOX_DELIVERY_ENABLED=false` (запись в Omnidesk: внутренние заметки, назначения, предупреждение клиенту за 15 минут, ссылка отмены). Приложение по умолчанию считает последний флаг **включённым**, поэтому ключ обязан быть задан явно: preflight без него не пройдёт.
- **Ручной запуск:** запуск и обновление выполняются вручную из чекаута репозитория на самом Raspberry Pi.

## 2. Первоначальная настройка и запуск

### Шаг 1: Подготовка конфигурации окружения
Скопируйте шаблон переменных окружения и задайте реальные локальные пароли и секреты:
```bash
cp deploy/stage/env.stage.example .env.stage
chmod 600 .env.stage
```

Отредактируйте `.env.stage`, заменив все плейсхолдеры `CHANGE_ME_*` на реальные значения (например, стойкий пароль к PostgreSQL и случайный ключ `APP_SECRET_KEY`).

### Шаг 2: Предварительная проверка окружения (Preflight)
Запустите диагностический скрипт:
```bash
./scripts/stage-preflight.sh --env-file .env.stage
```
Скрипт проверяет:
- Наличие Docker и Docker Compose;
- Архитектуру хоста (`uname -m`);
- Доступное дисковое пространство (не менее 5 ГБ);
- Права доступа к `.env.stage` (запрет доступа для группы "others");
- Заполненность обязательных переменных и отсутствие значений-плейсхолдеров;
- Безопасное состояние флагов доставки;
- Корректность синтаксиса Compose с наложением `docker-compose.stage.yml`;
- Чистоту отслеживаемых файлов в Git;
- Актуальный head миграций Alembic из исходного кода.

### Шаг 3: Развёртывание целевого релиза
Развёртывание выполняется с указанием точного коммита (полный 40-значный или сокращённый 7+ значный hex-хэш SHA):
```bash
# Пробный запуск без изменений (dry-run):
./scripts/stage-deploy.sh --sha 66c6439c8702 --env-file .env.stage --dry-run

# Боевое развёртывание:
./scripts/stage-deploy.sh --sha 66c6439c8702 --env-file .env.stage
```

Скрипт выполнит:
1. Запуск preflight-проверок;
2. `git fetch origin` и валидацию коммита;
3. `git checkout --detach <sha>`;
4. Сборку Docker-образов `rdm-backend:<release>` и `rdm-frontend:<release>` (где release — первые 12 символов SHA);
5. Запуск PostgreSQL и Redis и ожидание их готовности;
6. Применение миграций `alembic upgrade head`;
7. Запуск всего стека (backend, frontend, worker, beat);
8. Ожидание готовности backend (`/health/ready`) и доступности frontend;
9. Сохранение текущего и предыдущего тегов релиза в `deploy/stage/.state/`.

### Шаг 4: Создание первого администратора
На пустой базе нет ни одного пользователя, а административный интерфейс требует входа, поэтому первого администратора создаёт отдельная команда (из интерактивного терминала):
```bash
./scripts/stage-create-admin.sh --username admin --full-name "Администратор" --env-file .env.stage
```
Пароль (8–128 символов) вводится скрытно, передаётся в контейнер только через stdin и нигде не печатается; существующий логин команда не перезаписывает. Остальных пользователей и роли (L1, L2, руководитель) создавайте в интерфейсе `http://localhost:8080/admin`. Администратор сам по себе не видит карточки, для проверки бизнес-сценариев нужны отдельные пользователи с ролями L1, L2 и руководителя, участие L2 и L1 в распределении, графики работы.

## 3. Smoke-чек-лист после развёртывания

> **Omnidesk на стенде.** Создание карточек проверяет тикет через Omnidesk (чтение). Для проверки бизнес-логики задайте в `.env.stage` ключи **только на чтение** (`OMNIDESK_BASE_URL`, `OMNIDESK_STAFF_EMAIL`, `OMNIDESK_API_KEY`) и оставьте `OMNIDESK_OUTBOX_DELIVERY_ENABLED=false`: записи в Omnidesk при этом накапливаются в таблице `omnidesk_outbox` (их видно в БД), но в тикеты не уходят. Без ключей Omnidesk карточки создать нельзя.


После успешного деплоя выполните базовый ручной smoke-тест:

| Проверка | Точка входа / URL | Ожидаемый результат |
|---|---|---|
| **Health Liveness** | `http://localhost:8000/health/live` | `{"status": "ok", ...}` |
| **Health Readiness** | `http://localhost:8000/health/ready` | `{"status": "ok", "postgres": "ok", "redis": "ok"}` |
| **Авторизация / Логин** | `http://localhost:8080/` | Форма входа; успешный вход по логину/паролю, установка HttpOnly-куки |
| **Рабочее место руководителя** | `http://localhost:8080/manager` | Отображение списка карточек, фильтрация, распределение |
| **Рабочее место администратора** | `http://localhost:8080/admin` | Управление пользователями, графиками, каталогами |
| **Операционные отчёты** | `http://localhost:8080/reports` | Построение отчётов по карточкам и коллизиям за период |
| **Рабочее место инженера** | `http://localhost:8080/work` | Доступ к карточкам инженера L1/L2, взятие в работу |
| **Omnidesk Frame** | `http://localhost:8080/frame` и `/omnidesk-frame.js` | Загрузка клиентского фрейма |
| **Клиентская отмена** | `http://localhost:8080/cancel` | Форма подтверждения отмены по токену |

## 4. Пошаговое включение и проверка каналов доставки

Для тестирования внешней доставки уведомлений (Telegram, Битрикс24, Omnidesk):
1. Заполните необходимые реквизиты интеграции в `.env.stage` (токены, вебхуки).
2. Включайте **по одному** флагу и проверяйте результат на тестовом получателе или тестовом тикете:
   ```env
   NOTIFICATION_DELIVERY_ENABLED=true      # Telegram / Битрикс24
   REMINDER_SCANNER_ENABLED=true           # напоминания и эскалации
   OMNIDESK_OUTBOX_DELIVERY_ENABLED=true   # запись в тикеты Omnidesk (ТОЛЬКО тестовый тикет!)
   ```
3. Запустите preflight или deploy с явным разрешающим флагом:
   ```bash
   ./scripts/stage-deploy.sh --sha <sha> --env-file .env.stage --allow-delivery
   ```
4. Проверьте доставку на синтетической карточке.
5. После завершения тестирования **верните флаги в `.env.stage` в значение `false`** и повторите деплой (или `docker compose ... up -d`), чтобы worker и beat перечитали окружение.

## 5. Процедура отката (Rollback)

В случае сбоя или обнаружения регрессии на стенде:
```bash
# Пробный запуск отката (dry-run):
./scripts/stage-rollback.sh --env-file .env.stage --dry-run

# Выполнение отката к предыдущему релизу:
./scripts/stage-rollback.sh --env-file .env.stage
```

Если новый релиз накатил миграции БД, несовместимые со старым релизом, укажите ревизию для даунгрейда:
```bash
./scripts/stage-rollback.sh --env-file .env.stage --downgrade-to 20260930_0016
```

Скрипт `stage-rollback.sh`:
- Проверит наличие локальных образов предыдущего релиза;
- При необходимости выполнит `alembic downgrade` на текущем образе;
- Перезапустит сервисы с тегом предыдущего релиза;
- Дождётся готовности `/health/ready` и обновит статус в `.state/`.

## 6. Пересоздание базы данных с нуля (`--fresh`)

Если требуется полностью очистить базу данных тестового стенда и тома Docker Compose:
```bash
./scripts/stage-deploy.sh --sha <sha> --env-file .env.stage --fresh --yes-destroy-stage-data
```
> [!WARNING]
> Режим `--fresh` безвозвратно удаляет тома `postgres-data` и `redis-data` стенда. Использование флага `--yes-destroy-stage-data` обязательно.

## 7. Автозапуск через Systemd (опционально)

Для автозапуска стенда при перезагрузке Raspberry Pi подготовлен systemd-юнит `deploy/systemd/rdm-stage.service`:
```bash
sudo cp deploy/systemd/rdm-stage.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable rdm-stage.service
```

## 8. Гарантии безопасности скриптов

Скрипты стенда строго следуют следующим принципам:
- **Никогда не выводят значения секретов** в stdout/stderr или лог-файлы (выводятся только имена переменных и статус проверки).
- **Никогда не выполняют `git push` или SSH-подключения** во внешние репозитории/серверы.
- **Не используют небезопасные конструкции:** запрещены `eval`, `rm -rf`, `docker system prune`.
- **Изоляция Compose:** используется выделенный проект (`-p rdm-stage`), что исключает воздействие на другие Docker-контейнеры хоста.

## 9. Известные ограничения

1. **Omnidesk Frame:** для отображения фрейма внутри тикета в реальном Omnidesk требуется белый IP/домен с доверенным HTTPS-сертификатом, заполненный `CANCELLATION_PUBLIC_BASE_URL` и корректно сконфигурированные заголовки CSP (`frame-ancestors https://*.omnidesk.ru`). При локальном тестировании на RPi без внешнего HTTPS фрейм проверяется через прямой доступ по HTTP.
2. **Производительность SD-карты:** сборка Docker-образов на RPi 5 может занимать несколько минут; рекомендуется использовать быстрый накопитель (NVMe SSD или качественную microSD A2).
